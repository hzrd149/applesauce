# Migrating from v6 to v7

v7 separates single relay interactions from the methods that manage authentication, retries, and reconnects. Most application code should use `publish()`, `request()`, `subscription()`, and `sync()`; keep `event()`, `req()`, and `negentropy()` for callers that manage their own lifecycle.

## 1. Upgrade dependencies together

Upgrade every `applesauce-*` package your application uses to major version 7. The thirteen packages share the major version, while minor and patch releases remain independent.

React 18 is still supported; React 19 is also supported. The SDK is built with TypeScript 7, but upgrading your application's compiler is not a required migration step.

The examples below assume existing `relay`, `pool`, `relays`, `filters`, `eventStore`, and `signer` values. Imports are shown when a new API is introduced.

## 2. Move relay policy to the high-level methods

| v6 usage                                                | v7 migration                                          |
| ------------------------------------------------------- | ----------------------------------------------------- |
| `event()` for publishing with automatic auth handling   | Use `publish(event, options)`                         |
| `event(event, "AUTH")`                                  | Use `auth(event)`                                     |
| `req(filters, { waitForAuth, reconnect, resubscribe })` | Move those options to `request()` or `subscription()` |
| Group/Pool `count()` entries with `.count`              | Narrow `.ok`, then read `.value.count`                |
| Callback-based `negentropy()`                           | Consume negotiation rounds or use `sync()`            |
| `sync()` emitting events                                | Handle typed transfer messages                        |
| `pool.ignoreOffline` or `pool.group(relays, true)`      | Filter relay URLs with `ignoreUnhealthyRelays()`      |

### Publishing

`event(event)` sends one EVENT attempt and returns an Observable. It no longer accepts an EVENT/AUTH selector or manages authentication, retries, and reconnects. `auth(event)` sends one AUTH attempt and returns a Promise.

```ts
// Before
relay.event(signed, "AUTH").subscribe(handleResponse);

// After
const response = await relay.auth(signed);
handleResponse(response);
```

For application publishing, move to `publish()` and supply authentication policy there:

```ts
const response = await relay.publish(signed, {
  onAuthRequired: async ({ relay }) => {
    await relay.authenticate(signer);
  },
  timeout: 30_000,
});
if (!response.ok) showRejection(response.message);
```

A negative relay verdict normally resolves with `ok: false` and a typed `error`. Client failures, including transport failures and exhausted timeouts or authentication attempts, reject the single-relay Promise. Handle both rejection and `ok: false`; receiving a response does not mean the event was accepted. Group/Pool publishing converts individual relay failures into response entries.

### Requests and subscriptions

`req()` accepts only `{ id }` options and emits structured `OPEN`, `EVENT`, `EOSE`, and `CLOSED` messages. Group/Pool `req()` also emits `ERROR` messages. Raw requests do not authenticate, reconnect, or repeat automatically.

```ts
// Before
relay.req(filters, { reconnect: true, waitForAuth: true });

// After: finite query, emitting NostrEvent values
relay.request(filters, { reconnect: true, waitForAuth: true });

// After: persistent stream, emitting NostrEvent or "EOSE"
relay.subscription(filters, { reconnect: true, waitForAuth: true });
```

When replacing `req()` with a high-level method, remove handlers expecting structured messages. `request()` emits events. Single-relay `subscription()` emits events and the literal `"EOSE"`; Group/Pool subscriptions emit events only. Use `onlyEvents()` from `applesauce-relay/operators` when a single-relay subscription consumer expects only events.

`request()` defaults to a 30-second deadline over its entire lifetime. Events do not reset or disarm that deadline; an active authentication phase pauses the remaining budget. Set a larger `timeout` for slow finite requests. `subscription()` has no built-in timeout; use RxJS `takeUntil()` or `timeout()` to impose your application's lifetime or inactivity bound.

Raw `req()` completes on an ordinary CLOSED or clean socket close and errors on transport failures or error-prefixed CLOSED reasons. Unsubscribe to close a raw interaction; EOSE alone does not complete it.

### Group failures

Group/Pool `request()` and `subscription()` now error with `RelayGroupError` when every active relay fails. A successful finite query with no events still completes normally. Do not treat every completion/error path as an empty result.

```ts
import { RelayGroupError } from "applesauce-relay";

pool.request(relays, filters).subscribe({
  next: (event) => eventStore.add(event),
  error: (error) => {
    if (error instanceof RelayGroupError) reportFailures(error.outcomes);
    else reportError(error);
  },
});
```

`error.outcomes` contains causes keyed by normalized relay URL. Low-level Group/Pool `req()` retains message-based errors for callers managing their own policy.

### Group request completion

Group/Pool `request()` no longer completes five seconds after the first EOSE. It now defaults to `RelayGroup.completeAfterIdle()`, which runs from the first EOSE:

- it waits at least 3 seconds (`grace`) for relays that haven't responded;
- it keeps waiting while relays send events, and completes once no event has arrived for 1.5 seconds (`idle`);
- it stops after 15 seconds (`cap`).

A relay that sends no EVENT or EOSE within `firstResponseTimeout` (default 10 seconds) fails with `RelayFirstResponseTimeoutError`, so a group of silent relays errors with `RelayGroupError` instead of waiting for the whole-request timeout.

```ts
// Tune the default for a completeness-first request
pool.request(relays, filters, { complete: RelayGroup.completeAfterIdle({ grace: 5_000, cap: 30_000 }) });

// Restore the v6 behavior
pool.request(relays, filters, { complete: RelayGroup.completeAfterFirstRelay(5_000), firstResponseTimeout: false });
```

### Relay health filtering

Remove `pool.ignoreOffline` and the second argument to `pool.group()`. Filter the relay URL stream explicitly:

```ts
import { RelayLiveness } from "applesauce-relay";
import { ignoreUnhealthyRelays } from "applesauce-relay/operators";
import { of } from "rxjs";

const liveness = new RelayLiveness();
liveness.connectToPool(pool);
const healthyRelays$ = of(relays).pipe(ignoreUnhealthyRelays(liveness));
const group = pool.group(healthyRelays$);
```

See [relay liveness](/loading/relays/liveness) for persistence and health settings.

## 3. Authenticate per operation

Remove `authRequiredForRead$`, `authRequiredForPublish$`, and the matching `RelayStatus` fields. A refusal applies to the operation that received it. Use `onAuthRequired` on high-level operations, or watch `challenge$` to authenticate proactively.

```ts
relay.subscription(filters, {
  waitForAuth: pubkey,
  onAuthRequired: async ({ relay }) => {
    await relay.authenticate(signer);
  },
  authTimeout: 30_000,
  authRetries: 1,
});
```

`waitForAuth` now accepts `true` (any authenticated user), a pubkey, or an array of pubkeys (all required users). `false` fails immediately on an auth-required refusal. The default authentication phase is bounded to 30 seconds, including the handler; `authTimeout: false` disables that phase deadline. `authRetries` bounds consecutive auth-required cycles.

The handler receives `{ relay, url, challenge, request, requirement, missingPubkeys, reason }`. Narrow `request.verb` to inspect the refused REQ, COUNT, EVENT, or NEG-OPEN. Return or await authentication work so handler failures reach the operation's error path.

`authenticate()` now waits for a challenge and checks its freshness after signing:

```ts
const response = await relay.authenticate(signer, {
  timeout: 30_000,
  challengeRetries: 1,
  signal: controller.signal,
});
```

Its deadline includes challenge acquisition, signing, freshness retries, and the AUTH reply. `timeout: false` disables the outer deadline, while the low-level reply remains bounded. Negative AUTH verdicts resolve with `ok: false`; signer, freshness, timeout, transport, and abort failures reject.

For multiple accounts, use `authenticatedPubkeys$` and `authentications$`. The single-user `authenticatedAs$` API is deprecated.

## 4. Update COUNT consumers

Single-relay `count()` still emits a count response. Policy options are the third argument: `relay.count(filters, undefined, options)`.

Group/Pool COUNT now emits progressive snapshots of per-relay outcomes instead of a map of bare count responses. Pending relays have no entry; a failed relay has an error entry rather than disappearing.

```ts
pool.count(relays, filters).subscribe((outcomes) => {
  for (const [url, outcome] of Object.entries(outcomes)) {
    if (outcome.ok) showCount(url, outcome.value.count);
    else showCountError(url, outcome.error);
  }
});
```

Use `lastValueFrom()` if you need the final snapshot for a fixed relay list. Preserve successful results when another relay fails. Counts can include `approximate` and `hll`; adding per-relay counts can double-count events shared by relays.

## 5. Update negentropy and sync

### Raw negotiation

`relay.negentropy()` now returns an Observable of `{ have, need }` rounds. Remove the reconciliation callback argument and the old `NegentropySyncOptions` / `GroupNegentropySyncOptions` types. Raw options are `NegentropyOptions`: `id`, `frameSizeLimit`, and `signal`.

```ts
relay
  .negentropy(eventStore, filters, { frameSizeLimit: 60_000 })
  .subscribe(({ have, need }) => reconcileIds(have, need));
```

Observable completion does not wait for asynchronous subscriber callbacks. If your old reconciliation callback returned a Promise, compose that work with RxJS `concatMap()` or use managed `sync()` so completion includes transfers.

Here `filters` must be a single filter, rather than an array. Group and Pool no longer expose `negentropy()`; use their high-level `sync()` methods for coordinated transfers.

### Transfer outcomes

`sync()` now emits messages rather than bare events:

| Message        | Meaning                                                         |
| -------------- | --------------------------------------------------------------- |
| `received`     | Downloaded event in `.event`                                    |
| `sent`         | Accepted upload with `.event` and `.response`                   |
| `send-failed`  | Failed upload with `.event`, `.error`, and optional `.response` |
| `relay-failed` | Group/Pool member failure with `.from` and `.error`             |

```ts
import { SyncDirection } from "applesauce-relay";

pool.sync(relays, eventStore, filters, SyncDirection.BOTH).subscribe((message) => {
  if (message.type === "received") showReceived(message.event);
  else if (message.type === "sent") showSent(message.event);
  else reportError(message.error);
});
```

Writable stores receive downloaded events automatically. If you pass a read-only store or an event array and persist downloads separately, select `received` messages and extract `.event` before passing them to an event-store operator.

Sync owns authentication, reconnects, and bounded transfers. Use `concurrency` (default 4) to bound transfers within each relay and `batchSize` (default 500) to bound missing-ID requests. The old group-negentropy `parallel` option is removed; Group/Pool sync runs relays concurrently. Both must be positive finite integers. There is no whole-sync `timeout` option; use `signal`, unsubscribe, or compose an RxJS lifetime bound. Aborting through `signal` completes the stream.

## 6. Update custom models and event stores

Stores, models, and casts are now generic over the event type. Existing signed-event code using default generics continues to work. If a custom model specifies its store type explicitly, insert the event type before that store parameter:

| v6 type                             | v7 type                                         |
| ----------------------------------- | ----------------------------------------------- |
| `Model<T, TStore>`                  | `Model<T, NostrEvent, TStore>`                  |
| `ModelEventStore<TStore>`           | `ModelEventStore<NostrEvent, TStore>`           |
| `ModelConstructor<T, Args, TStore>` | `ModelConstructor<T, Args, NostrEvent, TStore>` |
| `EventModels<TStore>`               | `EventModels<NostrEvent, TStore>`               |
| `IEventModelMixin<TStore>`          | `IEventModelMixin<NostrEvent, TStore>`          |

Import `EventModels` from `applesauce-core`; import the other model types from `applesauce-core/event-store`; import `NostrEvent` from `applesauce-core/helpers`.

Explicit `verifyEvent: undefined` now disables EventStore verification. If your options builder previously included an undefined verifier to mean “use the default,” omit the property instead:

```ts
// Uses the default signature verifier
const events = new EventStore();

// Explicitly disables verification
const trustedEvents = new EventStore({ verifyEvent: undefined });
```

For unsigned NIP-59 rumors, use `RumorStore` or `AsyncRumorStore` instead of casting rumors to signed events. These stores check event hashes; the upstream protocol remains responsible for authorization.

Applesauce helper caches are now non-enumerable, so spreading an event no longer copies decrypted content or cached parsing results. Keep the original event instance when you need its decrypted state. Cache writes on frozen, sealed, or non-extensible events now throw; copy state-managed events before passing them to stores or helpers, for example `eventStore.add({ ...frozenEvent })`.

Malformed-content getters such as `getHiddenTags`, `getGiftWrapSeal`, `getSealRumor`, `getTokenContent`, `getHistoryContent`, `getNutzapP2PKPubkey`, and `getWalletNotification` now return `undefined` instead of throwing. Replace exception-based fallbacks with return-value checks. Imperative unlock methods still throw. Gift-wrap helpers also verify seal signatures before trusting authorship; update unsigned or malformed seal fixtures.

`EventFactory.kind()` has been removed. Choose the kind when constructing a builder with `EventFactory.fromKind(kind)`, or use the appropriate typed factory's `create()` method.

## 7. Replace logging controls

Applesauce logging no longer uses the `debug` package. If you controlled its logs through `debug.enable()` / `debug.disable()`, switch to the core exports:

```ts
import { enableLoggerNamespaces, disableLoggerNamespaces } from "applesauce-core";

enableLoggerNamespaces("applesauce:*");
disableLoggerNamespaces();
```

`DEBUG` in Node and the browser's `localStorage.debug` setting are still read when logging initializes. Use `setLoggerSink((message, record) => ...)` for a custom destination and import the `Debugger` type from `applesauce-core` for custom integrations.

## 8. Check signer and database integrations

`NostrConnectSigner` requests now reject after 60 seconds by default, when publishing fails, or when the signer closes. Set the signer's `timeout: 0` option only if you intend to disable its response deadline. Handle rejected signing/encryption requests in existing session flows.

For client-initiated `nostrconnect://` sessions, the remote signer must return the URI's secret in its connect response. A bare `"ack"` is no longer accepted. Update custom remote signers that implement this handshake; `bunker://` connect responses still use `"ack"`.

SQLite drivers are now optional peers. Install the backend your application imports, such as `better-sqlite3` for `applesauce-sqlite/better-sqlite3` or `@libsql/client` for `applesauce-sqlite/libsql`. Native Node and Bun drivers use runtime-provided SQLite. See [SQLite databases](/storage/databases/better-sqlite3) for driver usage.

## 9. Update social graph loading

`createSocialGraphLoader()` now returns `{ events$, status$ }` instead of an Observable of events. Subscribe to both in the same tick so they share one crawl; `status$` reports found, missing, and per-relay progress.

```ts
const { events$, status$ } = socialGraphLoader({ pubkey, relays, distance: 2 });

combineLatest([events$.pipe(tap((event) => graph.handleEvent(event))), status$]).subscribe();
```

The loader now loads batches of 100 users (`parallel`) with up to 6 batches in flight (`concurrency`) and at most 4 open requests per relay (`maxRequestsPerRelay`). Lists found through `cacheRequest` are refreshed from relays with a `since` after the cached list, and `events$` only emits a list when it is newer than the one already loaded for that user.

## Integration

Existing loaders should use the pool's high-level request path. Keep [EventStore loader wiring](/loading/loaders/unified-loader), and pass operation authentication options when loading from private relays. `createSyncLoader()` adapts the new sync messages and continues returning events. Custom `SyncSyncMethod` adapters must return `Observable<SyncResult>` and forward the optional third `SyncMethodOptions` argument; request adapters should forward their options argument too. Custom pool adapters must preserve terminal authentication failures rather than converting them into empty results; see [upstream pools](/loading/loaders/upstream-pool).

Keep factory signing and relay publishing as separate steps: the account manager's signer signs the event, while `publish()` handles relay policy. See [factories](/creating/factory/) and [relay pools](/loading/relays/pool).

## Best Practices

- Use high-level relay methods for application work; use raw methods when you own retries and cancellation.
- Choose a specific `waitForAuth` pubkey for private data in applications with multiple accounts.
- Render progressive COUNT outcomes by relay URL, replacing prior entries on each snapshot.
- Treat sync completion as the end of transfers; inspect failure messages before reporting success.
- Reuse one EventStore for related models, loaders, and React views.

## Verification

1. Search application code for `event(..., "AUTH")`, policy options passed to `req()`, removed auth-required flags, `ignoreOffline`, direct COUNT `.count` reads, negentropy callbacks, and sync consumers expecting events.
2. Update explicit custom model generic arguments and logging controls, then run your application's type checker.
3. Test finite requests, persistent subscriptions, all-relay failures, publish rejections, private-relay authentication, partial COUNT results, and cancelled syncs.
4. Test NIP-46 login and restored sessions against the remote signers your application supports, and verify the selected SQLite backend is installed.
