# Phase 25.3: Concord Invite-Bundle Rule-Table Hardening - Context

**Gathered:** 2026-09-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Strengthen Concord's invite-bundle validation and projection boundary so rule kinds are structurally tied to field types, optional fields retain their omission semantics, and corrupt self-authored invite data fails safely without damaging valid state.

</domain>

<decisions>
## Implementation Decisions

### Structural Rule Typing
- Derive each field's allowed rule from its declared value type so incompatible rule kinds fail at compile time.
- Model optionality separately from the field's value type and preserve omission rather than normalizing absent values.
- Apply the generic structural mechanism to every invite-bundle rule table, not only currently known mismatches.
- Prove the contract with compile-time assertions and generated runtime probes.

### Projection and Carry-Forward
- Rebuild validated bundles from declared rules and explicitly carry accepted optional fields; do not spread the source object.
- Drop unknown fields at the trust boundary.
- Keep absent optional fields absent through validation and projection.
- Derive projection coverage from the bundle type and its rule table so field drift becomes a compile-time failure.

### Corrupt Self-Authored Data
- Reject corrupt self-authored invite data with a typed diagnostic while preserving the last valid projection.
- Quarantine a corrupt entry without poisoning independently valid invite-list entries.
- Do not silently repair or rewrite corrupt data; recovery occurs through an explicit later valid write.
- Add regression coverage for malformed persisted data, mixed valid and corrupt entries, and recovery after valid replacement.

### the agent's Discretion
- Choose the exact conditional and mapped type vocabulary used to bind field values to rule kinds.
- Choose the typed diagnostic shape and internal quarantine representation, consistent with existing Concord error conventions.
- Choose whether compile-time assertions live beside the implementation or in focused type-test fixtures.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `packages/concord/src/helpers/invite-bundle.ts` already owns the shared build/validate boundary and exhaustive invite-bundle rule tables.
- `InviteBundle`, `JoinMaterial`, `ChannelKey`, and `HeldKeyEntry` in `packages/concord/src/types.ts` provide the authoritative declared field types.
- `packages/concord/src/helpers/__tests__/invite-bundle-schema.test.ts` already generates probes from the rule tables and checks coverage.

### Established Patterns
- Concord closes validation defect classes with exhaustive mapped types and rebuild-never-spread projections.
- TypeScript strict mode and generated Vitest probes jointly enforce compile-time and runtime behavior.
- Validation occurs at attacker-controlled boundaries; optional values use `undefined`/omission rather than `null`.

### Integration Points
- Both URL invite bundles and Direct Invites share `buildInviteBundle` and `validateInviteBundle`.
- `ConcordClient.joinByLink`, direct-invite ingestion, and invite-list projections consume the validated shapes.
- Existing helper and client test suites cover rule-table behavior, join paths, and self-encrypted invite-list persistence.

</code_context>
