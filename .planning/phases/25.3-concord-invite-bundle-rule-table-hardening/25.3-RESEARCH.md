### Structural Rule Typing
- Derive each field's allowed rule from its declared value type so incompatible rule kinds fail at compile time.
- Model optionality separately from the field's value type and preserve omission rather than normalizing absent values.
- Apply the generic structural mechanism to every invite-bundle rule table, not only currently known mismatches.
- Prove the contract with compile-time assertions and generated runtime probes.

### Projection and Carry-Forward
- Rebuild validated bundles from declared rules and explicitly carry accepted optional fields; do not spread the source object.
- Drop unknown fields at the trust boundary.
- Keep absent optional fields absent through validation and projection.
- Derive projection coverage from the bundle type and its rule table so field drift becomes a compile-time failure.

### Corrupt Self-Authored Data
- Reject corrupt self-authored invite data with a typed diagnostic while preserving the last valid projection.
- Quarantine a corrupt entry without poisoning independently valid invite-list entries.
- Do not silently repair or rewrite corrupt data; recovery occurs through an explicit later valid write.
- Add regression coverage for malformed persisted data, mixed valid and corrupt entries, and recovery after valid replacement.

## Summary

The existing implementation already has the right runtime architecture: four rule tables rooted in `InviteBundle`, an exhaustive `switch` over rule kinds, and a rebuild-never-spread walker that drops unknown keys. Its remaining structural gap is localized in `ExhaustiveBundleRules<T> = { [K in keyof Required<T>]: BundleFieldRule }`: the mapping enforces the key set but never uses `T[K]`, so any field can select any rule kind. [VERIFIED: `packages/concord/src/helpers/invite-bundle.ts`] Official TypeScript documentation confirms that mapped types can compute each output property from indexed access `T[K]`, and conditional types can select a different rule union for each value shape. [CITED: https://www.typescriptlang.org/docs/handbook/2/types-from-types.html] [CITED: https://www.typescriptlang.org/docs/handbook/2/conditional-types]

The second defect class is in the self-authored Invite List projection. `parseInviteList` intentionally preserves its open wire document; `ConcordInviteManager.reconcile()` currently merges raw entries, and `emit()` maps every entry through `fromInviteListInvite`, which calls `hexToBytes(invite.signer_sk)` without isolating failures. One corrupt entry can therefore throw during the whole emission and prevent valid siblings from being projected. [VERIFIED: codebase grep] The phase should add a closed, allowlist-rebuilt validator for each persisted entry, keep wire-document preservation separate, retain the last valid public projection on corrupt replacement, and expose typed per-entry diagnostics through an observable consistent with Concord's existing `RotationDiagnostic` pattern. [VERIFIED: `packages/concord/src/client/rotation.ts`]

**Primary recommendation:** Implement `RuleFor<Value>` plus an optionality-aware mapped table type using `satisfies`, then add a pure Invite List entry validator and a manager-level valid/quarantined reconciliation step that commits atomically only after validation.

### Pattern 1: Value-Bound Rule Tables

**What:** Derive legal rule variants from a field's declared value type, after separating `undefined` from the underlying value. Preserve optionality as a separate constraint on `onAbsent`. [CITED: https://www.typescriptlang.org/docs/handbook/2/conditional-types]

**When to use:** Every one of the four invite-bundle rule tables.

```typescript
type Present<V> = Exclude<V, undefined>;
type RuleFor<V> = Present<V> extends string
  ? StringRule
  : Present<V> extends number
    ? IntegerRule
    : Present<V> extends readonly unknown[]
      ? ArrayRuleFor<Present<V>>
      : ObjectRuleFor<Present<V>>;

type BundleRules<T> = { [K in keyof Required<T>]: RuleFor<T[K]> };
```

The concrete aliases must discriminate array/object positions sufficiently to distinguish relay, channel, held-key, and blob-pointer rules; do not collapse all arrays or objects to one permissive branch. [VERIFIED: existing four runtime rule kinds]

### Pattern 2: Literal-Preserving Conformance

**What:** Declare each table literal with `satisfies BundleRules<Subject>` instead of an annotation that widens `kind`. [CITED: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html]

```typescript
export const INVITE_BUNDLE_FIELD_RULES = {
  community_id: { kind: "hex-key", onInvalid: "reject", onAbsent: "reject" },
  // ...
} satisfies BundleRules<InviteBundle>;
```

**When to use:** All exported `*_FIELD_RULES` tables and any compile-time probe that needs field-specific literal kinds.

### Pattern 3: Validate, Stage, Commit

**What:** Convert each raw persisted entry into either a closed valid value or a typed corrupt result, construct the full next projection in locals, then update manager state/observables only after the batch is safe. A corrupt entry is excluded without changing valid siblings; a corrupt replacement must not erase the prior valid projection. [VERIFIED: locked phase decisions]

**When to use:** `ConcordInviteManager.reconcile()` and its projection helper.

### Anti-Patterns to Avoid

- **Mapping every key to `BundleFieldRule`:** proves key coverage but not rule/value compatibility. [VERIFIED: current latent gap]
- **Using `Required<T>[K]` as the only optionality signal:** it removes the syntactic modifier, but rule selection and absence policy still need distinct derivations. [VERIFIED: phase decision]
- **Spreading attacker/self-persisted entries into validated output:** preserves unknown keys at the trust boundary. [VERIFIED: phase decision]
- **Catching around the whole map/reconcile:** one corrupt entry still suppresses valid siblings. [VERIFIED: current `emit()` structure]
- **Mutating manager state before the batch is validated:** makes preserving the last valid projection unreliable if a later conversion throws. [VERIFIED: codebase inspection]
- **Persisting a sanitized quarantine automatically:** violates explicit recovery and may destroy forensic/user data. [VERIFIED: locked phase decision]
- **Source-text regex as the sole compile-time proof:** retain direct compiler assertions; source scans are only a belt-and-suspenders non-vacuity check. [VERIFIED: existing test pattern]

## Common Pitfalls

### Pitfall 1: Optional Arrays Select No Rule

**What goes wrong:** `ChannelKey["held"]` and optional object fields include `undefined`, so a non-distributive conditional can fall through to `never`. [CITED: https://www.typescriptlang.org/docs/handbook/2/conditional-types]
**Why it happens:** Optionality and value shape are mixed in one conditional.
**How to avoid:** Select `RuleFor<Exclude<V, undefined>>`, then independently constrain `onAbsent` to `omit` for optional keys and reject/explicit normalization only for required keys. [VERIFIED: locked phase decision]
**Warning signs:** Optional fields require casts, or legal table entries unexpectedly resolve to `never`.

### Pitfall 2: `satisfies` Still Allows an Over-Broad Rule Union

**What goes wrong:** `satisfies` cannot help if `RuleFor<T[K]>` itself returns all rule kinds. [CITED: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html]
**Why it happens:** Key exhaustiveness is mistaken for semantic compatibility.
**How to avoid:** Add negative compile-time assertions for representative mismatches at every shape family, including the historical `refounder` string/`safe-integer` mismatch.
**Warning signs:** Intentionally changing `kind` to an incompatible variant still compiles.

### Pitfall 3: Explicit `undefined` Reappears

**What goes wrong:** Projection writes `{ key: undefined }`, changing own-key/value-hash behavior even though JSON serialization omits it. [VERIFIED: `rebuildByRules` documentation]
**Why it happens:** A generic object literal or unconditional assignment is simpler than conditional carry-forward.
**How to avoid:** Assign only `out[key] = value` outcomes and assert `hasOwnProperty` is false for absent optionals at every nesting level.
**Warning signs:** `toEqual` passes while own-key assertions fail.

### Pitfall 4: Quarantine Poisons or Rewrites the List

**What goes wrong:** A bad entry throws during `fromInviteListInvite`, or filtering marks state dirty and publishes a sanitized list. [VERIFIED: current manager flow; locked decision]
**Why it happens:** Wire ingestion, app projection, and persistence state share the same arrays.
**How to avoid:** Keep raw/canonical merge state distinct from the validated projected state; quarantine internally, emit a diagnostic, and do not call `markDirty()`/`save()` because of validation failure.
**Warning signs:** A corrupt remote event triggers a kind-13303 publish, clears `entries$`, or suppresses a valid sibling.

### Pitfall 5: Recovery Is Permanently Memoized

**What goes wrong:** Quarantine keyed only by token prevents a corrected later edition from being retried. [VERIFIED: analogous retry fingerprint logic in `ConcordClient.reconcileCommunities`]
**Why it happens:** The system remembers identity but not content/version.
**How to avoid:** Fingerprint the corrupt raw entry (canonical JSON is already used in the client) and retry when its material changes; clear quarantine after valid replacement.
**Warning signs:** A corrected entry remains absent until restart.

### Atomic per-entry projection

```typescript
const next: ConcordInviteLink[] = [];
for (const raw of document.entries) {
  const valid = validateInviteListEntry(raw);
  if (!valid) {
    quarantine(raw, event.id);
    continue;
  }
  next.push(projectInvite(valid, tombstones));
}
commitProjection(next);
```

This is a planning pattern, not a prescribed API signature; preservation of a prior valid value for a corrupt replacement must be applied before `commitProjection`. [VERIFIED: locked phase decisions]

## Open Questions (RESOLVED)

1. **Should a corrupt replacement be matched to the prior valid entry only by token, or by another stable identity?**
   - What we know: CORD-05 uses token as the Invite List merge key, and existing merge helpers dedupe by token. [VERIFIED: `packages/concord/src/helpers/invite-list.ts`]
   - What's unclear: A corrupt object may itself have an invalid/missing token.
   - **RESOLVED:** Preserve by token only when the raw token is a valid bounded token; otherwise quarantine without replacing any prior entry. Never infer identity from secret-key conversion that can throw.

2. **Should diagnostics be public on `ConcordInviteManager`?**
   - What we know: The locked decision requires a typed diagnostic, and rotation exposes public typed diagnostics. [VERIFIED: phase context; `rotation.ts`]
   - What's unclear: No invite-manager diagnostic surface exists today.
   - **RESOLVED:** Add `diagnostics$` as a public `Observable<InviteListDiagnostic>` and export its type through `client/index.ts`; keep quarantine storage private.
