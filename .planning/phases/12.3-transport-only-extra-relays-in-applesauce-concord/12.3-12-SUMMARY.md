# Phase 12.3 Plan 12: Gap Closure — Invite Bundle Cardinality/Length Bounds, Validation-Boundary joinByBundle, Relay Gate Relocation, and Self-Cleaning ExtraRelays Summary

**Count-capped held_roots/channels[].held and length-capped name/label/creator_npub in validateInviteBundle; joinByBundle now revalidates; the untrusted-relay filter moved off the app's own configured relays; leave() prunes a byte-capped-wedged Community List; ConcordCommunity's constructor and reconcileCommunities stop leaking/re-leaking ExtraRelays subscriptions.**

## Accomplishments

- `held_roots` and every `channels[].held` array are now count-capped on the RAW array, before any per-entry validation, at the same boundary that already capped `channels` — closing the ~800-sequential-networked-epoch-sync DoS and the per-channel ECDH-derivation storm (CR-01)
- Every attacker-controlled display/attribution string (`name`, `label`, `creator_npub`, `channels[].name`) that reaches the serialized Community List or a published Guestbook Join is now length-bounded at the validator, and `leave()` prunes an already byte-capped-wedged entry's bytes (not just its liveness) so the Community List can publish again (CR-02, both halves)
- `joinByBundle` is now itself a validation boundary — it calls `validateInviteBundle` and throws on failure — closing the gap where a public API accepted an unvalidated bundle (WR-02); the untrusted-relay predicate moved from `joinFromBundle`'s fallback branch (which was filtering the app's own trusted configured relays) to `joinByLink`'s bootstrap-relay selection, the genuinely untrusted producer (WR-03, folded in per the plan's scope table)
- `ConcordCommunity`'s constructor now disposes its `ExtraRelays` holder on any later construction failure, and `reconcileCommunities` fingerprints a failed entry's material so a repeatedly-failing Community List entry is attempted once per distinct material rather than once per cast emission (WR-01)

## Decisions Made

- Count caps and the text-length cap set to `64` and `256` respectively per the plan's explicit values, named with the existing `INVITE_BUNDLE_*` prefix
- Top-level `name` rejects the whole bundle when invalid (required field, cannot drop-to-undefined); `label`/`creator_npub`/`expires_at` drop to `undefined` (optional, mirrors the existing `refounder` precedent); `channels[].name` drops the entry (a type predicate cannot rewrite the value it inspects, D-01)
- `saveCommunityList`'s over-cap diagnostic measures the serialized byte count exactly ONCE and reuses that value for both the cap check and the message, rather than calling `communityListWithinByteCap` and then independently re-serializing for the message (which could diverge); the pre-existing `console.warn` and the new `this.publishLog` call now carry the identical detailed message rather than two different-detail reports
- `leave()` derives the tombstone before pruning `this.list` (comment states the order is deliberate, though `leaveCommunity` itself does not depend on it); liveness-safety of the prune rests on `removed_at = Date.now()` always being the latest possible timestamp at leave-time, so any stale re-merge's `added_at` cannot outrank it short of a genuine, later re-join
- `ConcordCommunity`'s constructor try/catch calls only `this.extras.dispose()`, never the full `dispose()`, since the instance is half-built and other fields may not exist yet
- `reconcileCommunities` fingerprints on the MATERIAL (`canonicalJson(community.current)`), not the `community_id` alone, clearing the record both on successful construction and on reap, so a corrected entry is retried and a stale failure record never blocks a future re-add

### Process deviation (not a Rule 1/2/3 auto-fix — a self-correction during execution)

**1. saveCommunityList diagnostics: reconciled duplicate-detail logging and reused a single byte measurement**

- **Found during:** Task 2, after an initial implementation of the over-cap diagnostic
- **Issue:** The first pass left the pre-existing generic `console.warn` directly beneath a new, more detailed `this.publishLog` message — the same over-cap condition would have reported twice with different detail. It also independently re-serialized `{ entries: list, tombstones }` a second time for the diagnostic byte count, duplicating `communityListWithinByteCap`'s own serialization with no guarantee the two stay in sync.
- **Fix:** Measured the serialized byte count once via a local `serializedBytes` computation, used that same value both for the cap comparison (replacing the `communityListWithinByteCap` call, whose import was removed as it became unused) and for the diagnostic message; `console.warn` and `this.publishLog` now emit the identical detailed message string.
- **Files modified:** `packages/concord/src/client/client.ts` (part of Task 2's commit)
- **Verification:** Full suite green (396 tests at Task 2's commit), acceptance-criteria greps for the relocated relay gate and validation boundary all passed
- **Committed in:** `7f4d0af9` (Task 2 commit)
