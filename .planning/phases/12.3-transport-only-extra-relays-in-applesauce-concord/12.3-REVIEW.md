## Critical Issues

### CR5-01 (BLOCKER): a rule's `kind` is not type-connected to the field it governs — a table can be provably exhaustive, provably key-exact, and provably path-rooted while being wrong; reproduced with the full gate green

**Files:** `packages/concord/src/helpers/invite-bundle.ts:361` (`ExhaustiveBundleRules<T>`), `:481-488` (`HELD_KEY_FIELD_RULES`), `:379-387` + `:515-521` (`RuleTableKeysExactly` / `RULE_TABLE_SUBJECT_PROOF`), `:663-686` (`validateInviteBundle`'s doc comment, which states a guarantee this finding falsifies), `packages/concord/src/helpers/__tests__/invite-bundle-schema.test.ts:107-173` (the generated probes, which cannot catch it by construction).

**Defeats:** D-17's ruling as restated by plan 14, and `validateInviteBundle`'s own shipped doc comment. That comment (`invite-bundle.ts:679-684`) claims the enforcement "is threefold (CR4-01): the mapped-type tables above (a field with no rule fails `tsc`), `RULE_TABLE_SUBJECT_PROOF` (a table whose key set has drifted from the real position it governs fails `tsc`), and the conformance suite (`invite-bundle-schema.test.ts` — **a rule that does not actually bound its field** … fails a test)." The third clause is false.

**Issue:** all three shipped mechanisms reason about **key sets and annotation text**, never about **types**:

- `ExhaustiveBundleRules<T> = { [K in keyof Required<T>]: BundleFieldRule }` (`:361`) — the value type is the *whole* `BundleFieldRule` union for every key. `T[K]` is never consulted. `root_epoch: { kind: "bounded-text", … }` on a `number` field, or `channels: { kind: "hex-key", … }` on an array field, are both perfectly well-typed.
- `RuleTableKeysExactly` (`:379-387`) compares `keyof Table` against `keyof Required<Shape>` in both directions. It is a **key-set** proof only, by its own definition. It cannot see rule *values*.
- The source-level meta-test (`invite-bundle-schema.test.ts:432-469`) reads the annotation *text* (`ExhaustiveBundleRules<…>` and whether the subject is path-rooted). It never evaluates a single rule.
- The generated conformance probes (`:107-173`) are `describe.each(Object.entries(…FIELD_RULES))` — they build a hostile value **from the rule's own `kind`** (`hostileValueFor`, `:79-101`) and assert the rule's **own declared disposition** fires. A rule is therefore always self-consistent under this suite: the suite is incapable of disagreeing with the table, because the table is its oracle.

**I reproduced it.** One-token edit, `invite-bundle.ts:487`, on a field declared `refounder?: string` (`types.ts:148`):

```diff
 export const HELD_KEY_FIELD_RULES: ExhaustiveBundleRules<BundleHeldRootEntry> = {
   epoch: { kind: "safe-integer", onInvalid: "reject", onAbsent: "reject" },
   key: { kind: "hex-key", onInvalid: "reject", onAbsent: "reject" },
-  refounder: { kind: "hex-key", onInvalid: "drop", onAbsent: "omit" },
+  refounder: { kind: "safe-integer", onInvalid: "drop", onAbsent: "omit" },
 };
```

```
$ pnpm --filter applesauce-concord build
$ tsc
(exit 0 — no error)

$ pnpm --filter applesauce-concord test
 Test Files  51 passed (51)
      Tests  471 passed (471)
```

Green across the board: `RULE_TABLE_SUBJECT_PROOF` (key set unchanged), the
source meta-test (annotation unchanged), the nested rule-coverage / nested
builder-coverage / nested unknown-key probes (all walk *keys*), and the generated
`held-root-entry field refounder` probe (which now feeds `Number.MAX_SAFE_INTEGER
+ 100` and asserts a drop — passing for the wrong reason). Reverted; `git status
--short` printed nothing.

**Consequence is behavioral, not cosmetic.** `checkKind`'s `safe-integer` case
(`:539-542`) requires `typeof raw === "number"`, so *every* legitimate 64-char-hex
`refounder` on a `held_roots` entry now fails the kind check and is dropped by
`applyFieldRule` (`:624`). `refounder` is the per-epoch attribution gate in
`helpers/guestbook.ts:101-103` (`if (refounder === undefined || d.author !==
refounder) continue;`) — it is what decides whether an epoch's Guestbook snapshot
(the joiner's only memberlist seed, per `buildInviteBundle`'s own doc at
`invite-bundle.ts:266-268`) is honored. So the shipped mechanism permits a
silent, zero-signal regression of the memberlist path.

**Coverage today is incidental, which is the tell.** I ran the identical mutation
on `INVITE_BUNDLE_FIELD_RULES.expires_at` (`safe-integer` → `bounded-text`,
`:447`): that one *is* caught — but by **five unrelated behavioral tests**
(`invite-bundle.test.ts:842`, `casts/__tests__/direct-invite.test.ts:51`, and
three others), not by any part of the D-17/CR4-01 mechanism. Whether a mis-kinded
rule is caught therefore depends entirely on whether some author happened to
write a behavioral test that reads that field back — which is precisely the
"author happened to think of it" property D-17 exists to eliminate. `held_roots[i].refounder`
is the field the round-4 review itself called "the hop no prior round inspected
at all" (`invite-bundle.ts:484`), and it is the one with no such test.

**Severity.** This does **not** reopen CR-01's security property: `rebuildByRules`
still iterates `Object.keys(table)` and never spreads input (`:649-661`), so no
unbounded attacker string reaches the document through this gap — it fails safe
(silent drop), exactly as CR4-01 did. It is rated BLOCKER on the identical basis
round 4 rated CR4-01: the phase's charter is that a *wrong bound is impossible to
ship silently*, this round's own shipped doc comment asserts that guarantee in
those words, and the guarantee is demonstrably false for the same shape, in the
same table, at the same position that has now caused four consecutive rounds of
misses. The fix is small and structural.

**Fix:** bind the rule union to the field's declared type, so a mis-kinded rule
becomes a compile error instead of a silent behavior change. This subsumes the
key-set proof rather than adding a fifth check:

```ts
/** The rule kinds that can validly bound a field of type `V`. A field whose
 *  type no branch matches resolves to `never`, forcing its author to add a new
 *  BundleFieldRule kind here AND a case in checkKind — the D-17 intent. */
type RuleFor<V> = [NonNullable<V>] extends [string]
  ? Extract<BundleFieldRule, { kind: "hex-key" | "bounded-text" }>
  : [NonNullable<V>] extends [number]
    ? Extract<BundleFieldRule, { kind: "safe-integer" }>
    : [NonNullable<V>] extends [readonly string[]]
      ? Extract<BundleFieldRule, { kind: "relay-list" }>
      : [NonNullable<V>] extends [readonly ChannelKey[]]
        ? Extract<BundleFieldRule, { kind: "channel-list" }>
        : [NonNullable<V>] extends [readonly HeldKeyEntry[]]
          ? Extract<BundleFieldRule, { kind: "held-list" }>
          : [NonNullable<V>] extends [BlobPointer]
            ? Extract<BundleFieldRule, { kind: "blob-pointer" }>
            : never;

export type ExhaustiveBundleRules<T> = { [K in keyof Required<T>]: RuleFor<Required<T>[K]> };
```

Then re-run the CR5-01 probe above (`hex-key` → `safe-integer` on
`HELD_KEY_FIELD_RULES.refounder`) and record the resulting `tsc` failure as the
acceptance evidence, exactly as plan 14's Task 3 did for probes 1-6. Also correct
`validateInviteBundle`'s doc comment (`:679-684`) so its third clause describes
what the suite actually proves ("a rule enforces its own declared disposition"),
not what it does not.

## Warnings

### WR5-01 (WARNING): the hand-enumerated-mirror class survives one hop downstream of the validator — `joinFromBundle`'s bundle→`JoinMaterial` projection and `buildInviteBundle`'s two literals

**Files:** `packages/concord/src/client/client.ts:664-697` (`joinFromBundle`'s `const material: JoinMaterial = {…}`), `packages/concord/src/helpers/invite-bundle.ts:275-283` (the per-channel projection) and `:286-300` (the bundle literal).

**Issue:** `joinFromBundle` builds the joined community's `JoinMaterial` by
hand-listing ten fields. A field added to `JoinMaterial`/`InviteBundle` is forced
into `INVITE_BUNDLE_FIELD_RULES` by `tsc` (D-17, working as designed) — but if it
is **optional**, `const material: JoinMaterial = { …ten fields… }` remains legal
with the new key absent, so the field is validated, bounded, and then silently
discarded on its way into the community engine. No build error, no test signal.
Structurally identical to CR4-01: a hand-written shape that *mirrors* a type
without being type-connected to it, at a position where drift is invisible.

The same holds twice inside `buildInviteBundle`: the channel projection (`:275-283`)
enumerates five `ChannelKey` keys, and the bundle literal (`:286-300`) enumerates
thirteen (`held_roots` deliberately omitted). An optional field added to
`ChannelKey` or `InviteBundle` compiles clean in both and is simply never minted.

This is currently *complete* at all three sites — I checked field-by-field against
`types.ts:145-186` — so this is a mechanism gap, not a live defect. It matters
because D-17's whole premise is that completeness here must not depend on the next
author noticing.

**Fix:** make each projection total by construction rather than by enumeration.
The cheapest form for `joinFromBundle` is to name the discards explicitly so the
compiler enforces the partition:

```ts
// client.ts — every InviteBundle key must be either carried or explicitly discarded.
const { icon: _icon, expires_at: _exp, creator_npub: _npub, label: _label, ...carried } = bundle;
const material: JoinMaterial = {
  ...carried,
  channels: bundle.channels ?? [],
  relays: bundle.relays.length ? [...bundle.relays] : [...fallbackRelays],
  held_roots: bundle.held_roots ?? [],
};
```

A new optional field then lands in `carried` automatically; a new field that must
*not* be carried forces an explicit destructured discard. Apply the equivalent to
`buildInviteBundle`'s channel projection (spread `channel`, then override), or —
if enumeration is preferred there for the deliberate `held_roots` omission — add
a `satisfies`-backed keyset assertion mirroring `RULE_TABLE_SUBJECT_PROOF`.

### WR5-02 (WARNING): plan 14's new `HeldKeyEntry` doc comment asserts a guarantee the validator does not enforce — the WR4-02 defect class, reintroduced by the WR4-02 sibling fix

**File:** `packages/concord/src/types.ts:141-143` (the claim), enforced-by: nothing; contradicted by `packages/concord/src/helpers/invite-bundle.ts:471` + `:574-594` + `:481-488`.

**Issue:** the newly-added `HeldKeyEntry` doc states: *"`refounder` is per-epoch
attribution … and is therefore only ever populated on `held_roots` entries; **a
channel's retained keys never carry it**."* Traced against the code, "never" is
false for the input that matters. `CHANNEL_KEY_FIELD_RULES.held` (`:471`) is
`kind: "held-list"`; `checkKind`'s `held-list` case (`:589`) hard-binds that kind
to `HELD_KEY_FIELD_RULES`, whose `refounder` rule (`:487`) is
`hex-key`/`drop`/`omit`. So an attacker-crafted bundle carrying
`channels[i].held[j].refounder = "<64 hex>"` is **accepted and copied through** to
the validated output, flows into `JoinMaterial.channels[].held[]` via
`joinFromBundle` (`client.ts:670`), and is serialized twice per Community-List
entry (`seed` + `current`). The type itself now permits it too — `ChannelKey.held`
is `HeldKeyEntry[]`, and `HeldKeyEntry.refounder` is optional, not `never`.

Impact is bounded (hex-key, and the 8192-byte whole-bundle cap holds), so this is
not a size or injection issue. It is the same failure WR4-02 was raised for: a
comment in the phase's most security-sensitive file stating an absolute the code
does not hold — the exact pattern that produced three rounds of falsified blanket
claims.

**Fix:** state what is true — the codebase never *emits* `refounder` at the channel
position, and the shared table deliberately *accepts* it there:

```ts
/** `refounder` is per-epoch attribution … Nothing this codebase mints ever emits
 *  it on a channel's retained keys; the shared HELD_KEY_FIELD_RULES table
 *  nonetheless accepts (and strips-on-invalid) it at BOTH positions, so an
 *  attacker-supplied bundle may carry one at `ChannelKey.held[]` — it is inert
 *  there (no consumer reads it) and bounded by the same hex-key rule. */
```

If it should genuinely be impossible at that position, that requires a distinct
rule table for `channels[].held[]`, which `RULE_TABLE_SUBJECT_PROOF` entry 4 would
then police — a design change, not a comment fix.

### WR5-03 (WARNING): `RULE_TABLE_SUBJECT_PROOF` is a hand-enumerated five-position tuple, and the source meta-test's discovery regex has two silent bypasses

**Files:** `packages/concord/src/helpers/invite-bundle.ts:515-521`, `:595-598` (`blob-pointer`'s hard-bound child table), `packages/concord/src/helpers/__tests__/invite-bundle-schema.test.ts:439` (the discovery regex), `:455` (the `>= 4` vacuity guard).

**Issue, three parts:**

1. **The proof enumerates positions.** Nothing forces a sixth tuple entry when a
   sixth nested object position is added to `InviteBundle`. Concretely: add
   `banner?: SomeBlob` where `SomeBlob` has a field `icon`'s `BlobPointer` lacks.
   `tsc` forces a rule (good); the natural rule is `kind: "blob-pointer"`; but
   `checkKind` (`:596`) hard-binds that kind to `BLOB_POINTER_FIELD_RULES`, typed
   over `NonNullable<InviteBundle["icon"]>`. The extra field is silently dropped —
   no annotation error (the table is still key-exact for `icon`), no proof entry
   (the tuple is five long), and no test (`baselineBundle()` at
   `invite-bundle-schema.test.ts:39-69` is a hand-written literal, so the nested
   coverage probes never see the new field either). Every tripwire is
   position-enumerated or fixture-dependent.

2. **The meta-test only discovers `export const <NAME>_FIELD_RULES`** (`:439`). A
   table declared as a non-exported `const`, or named anything else (e.g.
   `BANNER_RULES`), is invisible to it — and a non-exported table is perfectly
   usable from `checkKind`. The `expect(discovered.length).toBeGreaterThanOrEqual(4)`
   guard (`:455`) catches a regex that stops matching *existing* tables; it cannot
   catch one that never matches a *new* table.

3. **The alias check is a substring test.** `aliasMatch[1].includes("InviteBundle")`
   (`:462`) passes for any alias whose right-hand side merely *mentions* the string
   — including inside a comment, since the collapsed source retains comments and
   `([^;]+)` captures whatever precedes the first `;`.

I also confirmed a proof-degradation mode empirically: adding `[k: string]: unknown`
to `InviteBundle` — a pattern used by **four sibling interfaces in the same file**
(`types.ts:201,207,229,234`) — builds clean (`tsc`, exit 0) and collapses all five
`RuleTableKeysExactly` entries to vacuous `true`s. Named fields are still caught by
the homomorphic mapped type, so this is not a hole for a named field; it is
evidence that the proof's strength is contingent on a property of `InviteBundle`
that this file's own conventions would casually violate.

**Fix:** derive the proof instead of listing it. A recursive type that visits every
object-valued position of `InviteBundle` and demands a governing table removes the
enumeration; failing that, at minimum (a) assert in the meta-test that the *set* of
`checkKind` child-table bindings equals the set of discovered tables, (b) drop
`export` from the regex and match `(?:export )?const`, and (c) strip `/* */` and
`//` comments from `collapsed` before the alias check. Add an explicit
"`InviteBundle` must not gain an index signature" note beside `:389-393`, whose
existing comment already relies on that property.

### WR5-04 (WARNING): `ConcordInviteManager.emit()` runs unguarded `hexToBytes`/`getPublicKey` on an unvalidated document field — one malformed `signer_sk` wedges invite creation and revocation for the account, and makes `dispose()` leak the extras subscription

**File:** `packages/concord/src/client/invite-manager.ts:328-341` (`fromInviteListInvite`), reached from `:319-325` (`emit`), `:296-306` (`reconcile`, inside the `start()` subscription), `:314-317` (`markDirty`), `:161-171` (`stop`), `:176-179` (`dispose`).

**Issue:** `fromInviteListInvite` calls `getPublicKey(hexToBytes(invite.signer_sk))`
on every entry, every emit. `invite.signer_sk` arrives from the decrypted kind-13303
document via `reconcile` → `mergeInvites`, and I verified `mergeInvites`
(`helpers/invite-list.ts:61-68`) validates **only** `typeof e.token === "string"` —
`signer_sk` is never checked for presence, hex-ness, or the 32-byte length
`getPublicKey` requires. `hexToBytes(undefined)` and `hexToBytes("zz…")` both throw.

Blast radius is wider than a single bad render, because `emit()` sits on the write
paths too:

- `markDirty()` → `emit()` throws, so `record()` (`:254-258`) and `tombstone()`
  (`:261-266`) never reach their `await this.save()`. That propagates out of the
  public `create()` (`:206`) and `revoke()` (`:215`) — **every** subsequent invite
  mint or revocation for the account throws, permanently, until the offending entry
  is removed by some other means.
- `stop()` (`:169`) calls `emit()` before returning, and `dispose()` (`:177`) calls
  `stop()` **before** `this.extras.dispose()` — so a throw in `emit()` skips
  `extras.dispose()` entirely, leaking the subscription to the app-supplied
  `extraRelays` source. That is the exact leak WR-01 was raised and fixed for in
  the other three engines' constructors (`private-channel.ts:179-210`,
  `invite-watcher.ts:169-193`); this path was never given the same treatment.
- `revoke()` at `:219` calls `fromInviteListInvite` directly on a caller-supplied
  `InviteListInvite`, so an app can trigger it without any document at all.

The document is self-encrypted, so this is a robustness/availability defect rather
than an attacker-controlled one — but CORD-05 §4 is explicitly an armada-compatible
wire format, so a peer client writing a differently-shaped `signer_sk` is a
realistic source.

**Fix:** make the derivation total, and make `dispose()` unconditional:

```ts
function fromInviteListInvite(invite: InviteListInvite, tombstones: InviteListTombstone[] = []): ConcordInviteLink {
  let signerPubkey = "";
  try {
    signerPubkey = getPublicKey(hexToBytes(invite.signer_sk));
  } catch {
    // A malformed signer_sk makes this ONE link unusable (revoke/refresh need the
    // secret) — it must never take down the whole list's derivation.
  }
  return { …, signerPubkey, … };
}
```

```ts
dispose(): void {
  try { this.stop(); } finally { this.extras.dispose(); }
}
```

Consider also rejecting non-hex `signer_sk` in `mergeInvites` alongside the
existing `token` guard, so the bad entry never enters `this.invites`.

### IN5-01 (INFO): `ConcordInviteManager.save()` records a publish as successful before it is

**File:** `packages/concord/src/client/invite-manager.ts:288-293`.

**Issue:** `this.pool.publish(...)` is fire-and-forget with a `.catch()` that only
logs; `this.publishedFingerprint = fingerprint` and `this.dirty$.next(false)` run
unconditionally on the next two lines. A publish that fails for every relay is
therefore recorded as published, and every later `save()` short-circuits at the
fingerprint check (`:272-275`) — the Invite List is never retried until its
*content* changes. `revokeBundle` (`:246`) awaits its publish; `save()` does not.

**Fix:** set `publishedFingerprint`/`dirty$` inside the promise's success path, or
