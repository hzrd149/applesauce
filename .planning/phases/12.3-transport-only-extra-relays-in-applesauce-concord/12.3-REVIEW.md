# Phase 12.3: Code Review Report

**Reviewed:** 2026-07-25T18:51:43Z
**Depth:** standard
**Files Reviewed:** 16

## Summary

Third adversarial pass over the transport-only `extraRelays` surface plus the
12.3-12 gap closure (CR-01 count caps, CR-02 text caps + wedge recovery, WR-01
constructor leak, WR-02 `joinByBundle` validation boundary, WR-03 relay-gate
relocation).

The four verification items handed down with this review resolve as follows:

1. **Caps upstream of the hop they protect?** The *count* caps (`held_roots`,
   `channels[].held`, `channels`) are correctly ordered on the raw arrays and do
   sit upstream of `buildChain` / `deriveChannelKeys`. The *length* caps do NOT
   cover the untrusted object — see **CR-01**. Four sibling strings on the same
   attacker-crafted bundle escaped the CR-02 sweep entirely, and the validator's
   own doc comment asserts the opposite of what it enforces.
2. **`joinFromBundle` call graph.** Verified: exactly two callers
   (`client.ts:623` in `joinByLink`, `client.ts:645` in `joinByBundle`) and no
   third. WR-03's removal of the filter is *not* a reachability regression.
   It did, however, leave a different hole — see **WR-02**.
3. **`leave()` prune / CORD-02 §8 liveness.** The liveness argument in the
   comment is sound in isolation, but the prune is neither *reachable* in the
   wedge case it exists for nor *durable* against an ordinary multi-device
   merge — see **CR-02**.
4. **Inlined byte measurement.** Semantically identical to
   `communityListWithinByteCap` (verified line-by-line: same
   `new TextEncoder().encode(JSON.stringify({ entries, tombstones }))`, same
   `LIST_MAX_BYTES`, complementary comparison). The helper is now dead in `src`
   — see **WR-04**.

Test quality is generally high (expected values are hand-derived from spec
constants; the non-vacuity notes are substantive rather than decorative). Two
tests, however, have been silently hollowed out by this pass's own source
changes and no longer exercise the property they name (**WR-06**, **WR-07**).

## Critical Issues

### CR-01: `validateInviteBundle` still admits four unbounded attacker strings — the Community-List wedge is not closed

**File:** `packages/concord/src/helpers/invite-bundle.ts:375-466` (specifically
`377`, `436`, `438`) — reached from `packages/concord/src/client/client.ts:658-686`

**Issue:**
The 12.3-12 sweep bounded `name`, `channels[].name`, `label`, and
`creator_npub` at `INVITE_BUNDLE_MAX_TEXT_LENGTH`. Every *other*
attacker-controlled string on the same untrusted object escaped:

| field | check today | reaches |
|---|---|---|
| `bundle.owner` | `typeof === "string"` only (line 377) | `JoinMaterial.owner` |
| `bundle.owner_salt` | `typeof === "string"` only (line 377) | `JoinMaterial.owner_salt` |
| `bundle.refounder` | `typeof === "string"` only (line 438) | `JoinMaterial.refounder` |
| each `bundle.relays[i]` | `isSafeInviteRelayURL` — shape only, no length | `JoinMaterial.relays` |

The owner proof does **not** bound `owner`/`owner_salt`. `communityId()`
(`helpers/crypto.ts:103-105`) computes
`sha256("concord/community" || hexToBytes(owner) || salt)`, and `@noble/hashes`'
`hexToBytes` imposes no maximum length — it rejects only odd length and non-hex
characters. An attacker therefore picks a 120 000-character hex `owner`,
computes the matching `community_id` themselves, and the bundle
**self-certifies successfully**. `owner` is never checked to be a 64-char
x-only pubkey, even though every other key-shaped field in this validator
(`community_root`, `channels[].id`, `channels[].key`, `held[].key`) goes through
`isHexKey`, which *does* enforce exactly 64 characters.

`isSafeInviteRelayURL` delegates its shape check to `isSafeRelayURL`, whose
`WEBSOCKET_URL_CHECK` regex has an **unbounded** path group
(`[-a-zA-Z0-9()@:%_+.~#?&/=]*`, `packages/core/src/helpers/relays.ts:38-39`), so
five multi-kilobyte `wss://a.example.com/aaaa…` entries survive the
`INVITE_BUNDLE_RELAY_CAP` slice intact.

Every one of these lands in `JoinMaterial` at `client.ts:658-686` and is then
serialized **twice per entry** (`seed` and `current`, `recordJoin:764-769`) into
the kind-13302 document that `saveCommunityList` hard-caps at `LIST_MAX_BYTES`
(65 535). One accepted invite permanently wedges the user's Community List:
`saveCommunityList` early-returns at `client.ts:1067`, so no membership change
(join, leave, epoch adoption) ever syncs across devices again. This is the
*exact* defect CR-02 was raised for — `invite-bundle.test.ts:332-335` even spells
out the mechanism for `name`.

The fix is also structurally incomplete for the fields that *were* bounded.
There is no aggregate bound on the material's serialized size at the join
boundary, and the per-field caps sum well above `LIST_MAX_BYTES / 2`: a
well-formed bundle at the NIP-44 plaintext ceiling (~65 535 bytes, mostly
`channels[]` — 256 channels each carrying up to 64 `held` keys is permitted)
yields ~64 KB of material, doubled to ~128 KB in the document. So even with zero
unbounded strings, a legal maximum-size bundle still wedges the list.

Finally, the function's stated contract is now false. Lines 364-366 assert:
*"After this function returns a bundle, no attacker-controlled array is
count-unbounded and no attacker-controlled string that reaches the serialized
document or a published event is length-unbounded (CR-01/CR-02)."* Four
counter-examples above.

**Fix:**
```ts
// 1. owner is an x-only pubkey — hold it to the same isHexKey rule every other
//    key-shaped field here already uses, BEFORE hexToBytes ever sees it.
if (typeof bundle.owner !== "string" || !isHexKey(bundle.owner)) return undefined;
// 2. owner_salt is 32 bytes (CORD-02 A.4) — 64 hex chars, not "any even-length hex".
if (typeof bundle.owner_salt !== "string" || !isHexKey(bundle.owner_salt)) return undefined;
// ... existing communityId owner proof ...

// 3. refounder is a pubkey; drop to undefined when it is not one (mirrors the
//    existing drop-to-undefined precedent) rather than accepting any string.
const refounder =
  typeof bundle.refounder === "string" && isHexKey(bundle.refounder) ? bundle.refounder : undefined;

// 4. bound each relay entry's LENGTH as well as its shape.
export const INVITE_BUNDLE_MAX_RELAY_URL_LENGTH = 512;
const relays = bundle.relays
  .slice(0, INVITE_BUNDLE_RELAY_CAP)
  .filter((r) => isSafeInviteRelayURL(r) && r.length <= INVITE_BUNDLE_MAX_RELAY_URL_LENGTH);
```
Close the structural half with an aggregate guard at the join boundary
(`client.ts:686`, immediately after `material` is built) so no future per-field
regression can re-open the wedge:
```ts
// The material is serialized TWICE per Community-List entry (seed + current).
const entryBytes = 2 * new TextEncoder().encode(JSON.stringify(material)).length;
if (entryBytes > LIST_MAX_BYTES / 2) throw new Error("invite material too large to record");
```
Add regression tests: a bundle with a 60 000-char hex `owner`, one with a
60 000-char relay path, and one with a 60 000-char `refounder`, each asserting
`validateInviteBundle` returns `undefined`.

### CR-02: the `leave()` byte-prune does not reach — and does not survive — the wedge it was added to recover from

**File:** `packages/concord/src/client/client.ts:707-741` (prune at line `736`),
interacting with `client.ts:921-946` (`watchLists`)

**Issue:**
Two independent gaps make the "recoverable through the public API alone" claim
false in exactly the cases that matter.

**(a) Unreachable without a running engine.** `leave()` opens with
```ts
const community = this.communities.get(cid);
if (!community) return;            // client.ts:708-709
```
so the prune at line 736 only ever runs for a community whose engine is *live*.
But the wedge state is precisely a state in which the engine often is **not**:
- an entry whose material `reconcileCommunities` skipped as unconstructable
  (`client.ts:996-1006`) has no engine, is fingerprint-suppressed from retry
  (`client.ts:995`), and can therefore never be pruned;
- `leave(cid)` called before `start()` or after `stop()` silently no-ops while
  the entry's bytes remain in `this.list` and in the persisted mirror.

**(b) Not durable against an ordinary merge.** `watchLists` unconditionally
re-merges the relay copy:
```ts
this.list = mergeCommunities(this.list, communities);   // client.ts:933
```
`mergeCommunities` is a `community_id`-keyed union that *never deletes*
(`helpers/community-list.ts:132-140`). So as soon as another device — one that
was offline during our leave — publishes a 13302 with a newer `created_at` that
still carries the entry, its **bytes come straight back** into `this.list`.
Liveness stays correct (our tombstone still outranks the stale `added_at`), but
the document is over cap again, `saveCommunityList` wedges again, and by (a)
`leave()` can no longer prune it because the reaped community has no engine.
The wedge is then permanent with no public-API escape.

The comment at `client.ts:722-735` argues only the *liveness* half of CORD-02
§8; the byte-durability half is never addressed, and no test covers the re-merge
(the test that claims to is vacuous — see **WR-07**).

**Fix:** make the prune a property of the *derived-dead* state rather than a
one-shot side effect of `leave()`, so it is both reachable and idempotent:
```ts
async leave(cid: string): Promise<void> {
  this.log("leave requested community=%s", cid.slice(0, 8));
  // Tombstone + reap unconditionally — a membership with no running engine
  // (unconstructable material, pre-start, post-stop) must still be leavable.
  await this.communities.get(cid)?.leave();
  this.removeCommunity(cid);
  this.tombstones = leaveCommunity(cid, Date.now())(this.list, this.tombstones).tombstones;
  this.pruneDeadEntries();
  await this.saveMirror();
  await this.saveCommunityList();
}

/** Drop the BYTES of every entry already derived-dead (CORD-02 §8 liveness is
 *  carried by the tombstone, which is never pruned). Idempotent, so a stale peer
 *  re-merging a dead entry has it re-pruned on the next reconcile. */
private pruneDeadEntries(): void {
  this.list = this.list.filter((e) => isCommunityLive(this.list, this.tombstones, e.community_id));
}
```
Call `pruneDeadEntries()` at the end of `reconcileCommunities()` and after the
merge in `watchLists`, so a re-merged dead entry is pruned again before the next
save. Add tests for: `leave()` on a cid with no running engine, and a stale
remote copy published at a **newer** `created_at` than our own.

### WR-01: `ConcordPrivateChannel` has the identical `ExtraRelays` constructor leak that was fixed only in `ConcordCommunity`

**File:** `packages/concord/src/client/private-channel.ts:157-159`

**Issue:** 12.3-12 wrapped `ConcordCommunity`'s constructor tail in
`try { … } catch { this.extras.dispose(); throw }` (`community.ts:390-502`)
because a throw after `new ExtraRelays(...)` strands a permanent subscriber on
the app's `extraRelays` source. The sibling engine has the same shape and was
not fixed:
```ts
this.extras = new ExtraRelays(options.extraRelays);                     // :157
this.channelKey = options.channelKey;
this.keys = deriveChannelKeys(options.material(), options.channelKey);  // :159 — throws
```
`deriveChannelKeys` calls `hexToBytes(channel.id)` and `hexToBytes(channel.key)`
(`helpers/keys.ts:656,668`), which throw synchronously on malformed hex.
Malformed `ChannelKey`s are reachable: `material.channels` restored from another
device's Community List is never validated (only *invite bundles* are), and
`spawnPrivateChannel` runs from `reconcilePrivateChannels` inside the `state$`
subscription — so each throw both leaks a subscriber and errors the
subscription. `InviteWatcher` (`invite-watcher.ts:161-180`) has the same
unguarded shape with lower throw risk.

**Fix:**
```ts
this.extras = new ExtraRelays(options.extraRelays);
try {
  this.channelKey = options.channelKey;
  this.keys = deriveChannelKeys(options.material(), options.channelKey);
  // … rest of the constructor …
} catch (err) {
  this.extras.dispose();
  throw err;
}
```
Mirror `community.test.ts`'s `countingExtrasSource` leak test for
`ConcordPrivateChannel` — that test exists only for the community engine today.

### WR-02: the loopback `ws://` carve-out now applies *only* to attacker-controlled input

**File:** `packages/concord/src/helpers/invite-bundle.ts:86,107-111`

**Issue:** `LOOPBACK_PLAINTEXT_WS` was introduced so the app's own local cache
relay (`ws://localhost:4869`) would not be discarded. WR-03 then removed the
`isSafeInviteRelayURL` filter from `joinFromBundle` — the only call site that
ever saw the app's *own* configured relays — and relocated it to `joinByLink`.
After that relocation `isSafeInviteRelayURL` is applied at exactly two places,
`decodeFragment:152` and `validateInviteBundle:436`, **both attacker-controlled
boundaries**. The carve-out therefore no longer protects any trusted input; it
only grants a remote invite the ability to plant `ws://localhost:<port>`,
`ws://127.0.0.1:<port>`, or `ws://[::1]:<port>` into `material.relays`, which
the client then dials (loopback port probing whose outcome is observable through
`connected$`, `community.ts:439`) and publishes into its own Community List.

**Fix:** either drop the loopback branch from `isSafeInviteRelayURL` outright, or
gate it behind an explicit opt-in and pass `false` from both untrusted
boundaries:
```ts
export function isSafeInviteRelayURL(entry: unknown, opts: { allowLoopback?: boolean } = {}): entry is string {
  if (typeof entry !== "string") return false;
  if (opts.allowLoopback && LOOPBACK_PLAINTEXT_WS.test(entry)) return true;
  return entry.startsWith("wss://") && isSafeRelayURL(entry);
}
```
Update `invite-bundle.test.ts:152-165` and `449-459` accordingly.

### WR-04: `communityListWithinByteCap` is now dead in `src`, with a hand-duplicated copy inline

**Files:** `packages/concord/src/client/client.ts:1066`,
`packages/concord/src/helpers/community-list.ts:165-172`

**Issue:** `saveCommunityList` inlines its own measurement, and the exported
helper is referenced from `src` only inside a comment (`client.ts:1060`) — its
sole remaining callers are tests. The two are semantically identical today
(verified), which is precisely the drift risk: a future change to the wire shape
or to `LIST_MAX_BYTES` semantics must be made twice, and the helper's own test
suite will keep passing while the real publish path diverges.

**Fix:** keep one definition and have it return the measurement so the
diagnostic can reuse it:
```ts
// community-list.ts
export function communityListByteSize(
  communities: CommunityListCommunity[],
  tombstones: CommunityTombstone[],
): number {
  return new TextEncoder().encode(JSON.stringify({ entries: communities, tombstones })).length;
}
export function communityListWithinByteCap(c: CommunityListCommunity[], t: CommunityTombstone[]): boolean {
  return communityListByteSize(c, t) <= LIST_MAX_BYTES;
}

// client.ts
const serializedBytes = communityListByteSize(list, tombstones);
if (serializedBytes > LIST_MAX_BYTES) { /* …existing diagnostic… */ }
```

### WR-05: `ExtraRelays.merge`'s diagnostic mislabels normalization-collapsed duplicates as "unparseable"

**File:** `packages/concord/src/helpers/relays.ts:144-153`

**Issue:** `rawUnionSize` is a `Set` over the **raw** strings while `merged` is
`mergeRelaySets`'s **normalized** output. Any pair differing only by
normalization (trailing slash, case, default port) collapses in `merged` but not
in `rawUnionSize`, so the log claims relays were dropped as unparseable when
they were merely deduplicated. `relays.test.ts:139-144` exercises exactly this
case (`wss://b.example.com` + `wss://b.example.com/`), so the misleading line
fires in the project's own suite. During an incident this points an operator at
the wrong cause.

**Fix:** normalize both sides before comparing (or drop the diagnostic —
`mergeRelaySets` already swallows the parse failure):
```ts
const merged = mergeRelaySets(base, this.current);
const normalizedUnionSize = mergeRelaySets([...base, ...this.current]).length;
if (merged.length !== normalizedUnionSize) { /* genuinely unparseable */ }
```

### WR-06: the CR-02 join-atomicity regression tests are now vacuous

**File:** `packages/concord/src/client/__tests__/client.test.ts` — describe
`"ConcordClient join atomicity + reconcile fault-tolerance (CR-02, gap closure 12.3-11)"`,
first two tests

**Issue:** Both drive `{ …bundle, community_root: "not-hex" }` through
`client.joinByBundle(...)` and assert no residue. They were written to pin
`recordJoin`'s engine-first ordering (`client.ts:762-771`) — the actual CR-02
fix. WR-02 then made `joinByBundle` call `validateInviteBundle` first
(`client.ts:643`), and `isHexKey("not-hex")` is false, so the call now rejects
with `"invite failed validation"` **before `joinFromBundle`/`recordJoin` is ever
entered**. The assertions still pass, but for a different reason: the
engine-first ordering has zero remaining coverage, and reversing it — the change
`client.ts:760-761` explicitly forbids — would fail no test.

**Fix:** exercise `recordJoin` with material that passes `validateInviteBundle`
but still throws inside `deriveConcordKeys`, and assert `this.list` is
unchanged. Alternatively keep the current tests as `joinByBundle`-validation
tests (renaming them accordingly) and add a *separate* atomicity test.

### WR-07: the "stale remote copy" leave test never performs the merge it names

**File:** `packages/concord/src/client/__tests__/client.test.ts` — test
`"an ordinary leave() still tombstones, still publishes, and the membership stays derived-dead after a later merge of a stale remote copy that still holds the entry"`

**Issue:** The stale list event is signed with `created_at: 1` and added to a
store that already holds our leave-time publication stamped at
`Math.max(now, previous + 1)` (`client.ts:1106`). Kind 13302 is replaceable, so
the `EventStore` keeps the newer event and the cast never emits the stale
content — `watchLists`'s `mergeCommunities` is never reached with the stale
entry. The test therefore proves nothing about re-merge, which is exactly the
CR-02(b) failure mode.

The final assertion compounds this:
```ts
expect(entry === undefined || entry.added_at <= tomb.removed_at).toBe(true);
```
is satisfied trivially by `entry === undefined` after the prune, so the
`added_at <= removed_at` half is never evaluated.

**Fix:** stamp the stale event *newer* than our publication (e.g.
`created_at: Math.floor(Date.now() / 1000) + 60`), assert the merge actually
happened, and split the disjunction into two individually meaningful
assertions.

### WR-08: `handleRemoved` tombstones without pruning, diverging from `leave()`

**File:** `packages/concord/src/client/client.ts:823-830`

**Issue:** An involuntary Refounding removal takes the same "membership is now
dead" transition as `leave()` but omits the byte prune added at
`client.ts:736`. An over-cap entry removed by refounding therefore keeps wedging
the document and — having no engine after `removeCommunity(cid)` — is beyond
`leave()`'s reach per CR-02(a). Two code paths for one state transition with
different document effects is also a standing maintenance hazard.

**Fix:** route both through the shared `pruneDeadEntries()` proposed in CR-02.

## Info

### IN-01: over-cap diagnostic ignores tombstone bytes and can name an empty community

**File:** `packages/concord/src/client/client.ts:1074-1083`

The "largest entry" scan iterates `list` only. A document pushed over cap by
`tombstones` reports a misleading culprit, and with an empty `list`,
`largestEntryId` stays `""` so the message ends with a bare `community=`.
Include the tombstone byte total, and omit the "largest entry" clause when
`list.length === 0`.

### IN-02: `decodeFragment` silently yields a zero-length token on a truncated fragment

**File:** `packages/concord/src/helpers/invite-bundle.ts:126-152`

Once the byte cursor runs past the buffer, `bytes[i++]` is `undefined`, `i`
becomes `NaN`, and `bytes.slice(NaN, NaN + 16)` returns an empty `Uint8Array` —
so `parseInviteLink` returns a 0-byte token that only fails much later, inside
`nip44.decrypt`. Assert `token.length === 16` before returning and throw a
specific error.

### IN-03: unbounded in-memory sets on a long-lived client

**File:** `packages/concord/src/client/client.ts:300,303`

`handledInvites` and `autoUnlocked` grow monotonically and are not cleared by
`stop()`. On a long session with an active inbox this is a slow leak; both exist
only to suppress duplicate work within one run, so clear them in `stop()`.

### IN-04: `joinFromBundle` aliases `this.defaultRelays` into `material.relays`

**File:** `packages/concord/src/client/client.ts:677`

`relays: bundle.relays.length ? bundle.relays : fallbackRelays` stores the
client's own `defaultRelays` **array reference** as the community's protocol
relay set, and `ExtraRelays.merge`'s identity fast path (`relays.ts:142`) then
hands that same reference to `pool.subscription` / `pool.publish`. Nothing
mutates it today, but a future in-place mutation would corrupt every community
at once. Copy: `relays: bundle.relays.length ? [...bundle.relays] : [...fallbackRelays]`.

### IN-05: unreachable defensive call in `ConcordClient.dispose()`

**File:** `packages/concord/src/client/client.ts:484`

`this.stop()` (line 481) sets `this.inviteWatcher = undefined` at
`client.ts:462`, so the trailing `this.inviteWatcher?.dispose()` can never fire.
The comment acknowledges it as defensive; consider deleting it, since dead
defensive code that *looks* load-bearing invites future readers to preserve the
wrong invariant.
