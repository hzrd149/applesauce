## Summary

This is the **fourth** adversarial pass over this phase. The third pass (`CR-01`,
`CR-02`, `WR-01`…`WR-08`, `IN-01`…`IN-05`, preserved verbatim below) found that
`validateInviteBundle` had, for the third round running, bounded whatever field
its author thought of and missed the next one. Ruling **D-17** ordered a
structural fix: exhaustive mapped-type rule tables plus an allowlist rebuild, so
"forgot a field" becomes a compile error or a test failure instead of a fourth
review catching it.

**Did D-17 work?** Mostly, and the mechanism is well-built where it applies.
`INVITE_BUNDLE_FIELD_RULES`, `CHANNEL_KEY_FIELD_RULES`, and
`BLOB_POINTER_FIELD_RULES` are genuinely exhaustive — verified **empirically**,
not by reading: I added a throwaway field to `InviteBundle` and confirmed `tsc`
fails naming the rule table (reproducing the SUMMARY's own demonstration), and
independently traced that `ChannelKey` and `BlobPointer` are real, exported,
directly-referenced interfaces, so the same guarantee holds for them by
construction. The walker (`rebuildByRules`) genuinely never spreads its input at
any level — top-level, `channels[]`, `held_roots[]`, `icon` — confirmed by
reading every code path; an unknown attacker key cannot reach `JoinMaterial`
anywhere in this file.

**But one of the four tables is not actually exhaustive**, and I proved it by
reproducing the exact failure mode D-17 exists to eliminate: **CR4-01
(BLOCKER)** below. The security property CR-01 cares about (no unbounded
attacker string reaches the document) still holds even through this gap — but
the *mechanism* — the thing this entire gap-closure round was built and staffed
around — silently fails to fire for exactly the two fields (`held_roots[]` and
`channels[].held[]` entries) that caused the most recent two review rounds'
misses in the first place. That is not a coincidental target.

CR-02 (both halves) is genuinely closed: `pruneDeadEntries()` is reachable
without a running engine (`leave()`'s guard is now document-keyed, verified by
reading `client.ts:736-760`), and is idempotent against a re-merge (verified
that `reconcileCommunities()`'s prune runs synchronously in the same turn as
`watchLists`' merge, per JS's run-to-first-`await` semantics). WR-01 through
WR-07 are genuinely closed, each verified independently (see the disposition
table below) — this is a materially stronger round than the third pass reviewed.

Two adjudications were requested; both are resolved below (see "Adjudications").
`pnpm --filter applesauce-concord build` and `pnpm --filter applesauce-concord
test` (466 tests) both pass cleanly, confirmed by direct execution, not by
trusting the SUMMARY.

## Critical Issues

### CR4-01 (BLOCKER): D-17's exhaustiveness guarantee does not actually hold for `held_roots[]`/`channels[].held[]` entries — empirically reproduced

**Files:**
`packages/concord/src/helpers/invite-bundle.ts:348-354` (`HeldRootEntry`, `HELD_KEY_FIELD_RULES` at `435-442`), `packages/concord/src/types.ts:140,155` (the real, anonymous, un-exported element types this table is supposed to guard), `packages/concord/src/helpers/__tests__/invite-bundle-schema.test.ts:257-276` (the one test that could have caught this, and does not).

**Defeats:** D-17, directly and specifically. D-17's must-have (`12.3-13-PLAN.md` frontmatter) reads: *"Adding a field to `InviteBundle` (or to `ChannelKey`, a `held_roots` entry, or `BlobPointer`) without declaring a bound for it FAILS — either `pnpm --filter applesauce-concord build`... or the conformance suite... A fifth forgotten field is no longer possible to ship silently."* This is false for a `held_roots`/`channels[].held` entry field, and I proved it by doing exactly what the SUMMARY's own "Acceptance — Demonstrated, Not Asserted" section did for the *top-level* bundle, but for this one:

**Issue:** Three of the four rule tables (`INVITE_BUNDLE_FIELD_RULES`, `CHANNEL_KEY_FIELD_RULES`, `BLOB_POINTER_FIELD_RULES`) are typed as `{ [K in keyof Required<X>]: BundleFieldRule }` where `X` is a **real, exported, directly-referenced interface** (`InviteBundle`, `ChannelKey`, `BlobPointer` in `types.ts`). Adding a field to any of those three interfaces genuinely fails `tsc`, because the mapped type is derived from the interface itself.

The fourth table, `HELD_KEY_FIELD_RULES`, is typed over `HeldRootEntry` — a type **hand-declared locally in `invite-bundle.ts`** (`type HeldRootEntry = { epoch: number; key: string; refounder?: string }`, line 354) that *mirrors* but is **never connected to** the real element types it is supposed to police: `ChannelKey.held?: Array<{ epoch: number; key: string }>` (`types.ts:140`) and `JoinMaterial.held_roots?: Array<{ epoch: number; key: string; refounder?: string }>` (`types.ts:155`). Both real types are anonymous inline object-literal types, not named/exported interfaces — because they aren't named, nothing in `invite-bundle.ts` can write `keyof Required<(that real type)>`, so the author wrote a duplicate instead. No assignment, call, or generic constraint anywhere in the codebase ties `HeldRootEntry` back to either real element type; the walker's own type-erasure (`rebuildByRules<T>` returns `out as T`, and `validateInviteBundle` finishes with `rebuilt as unknown as InviteBundle`) means TypeScript never checks the two against each other.

**I reproduced this, not just read it.** I added a field to each real type and ran the package's own build gate:

```
$ sed -i 's/held_roots?: Array<{ epoch: number; key: string; refounder?: string }>;/held_roots?: Array<{ epoch: number; key: string; refounder?: string; throwawayHeldField?: string }>;/' packages/concord/src/types.ts
$ pnpm --filter applesauce-concord build
$ rimraf dist
$ tsc
      # exit 0 — NO ERROR
```
and again for `ChannelKey.held`'s element type (`throwawayChannelHeldField?: string`) — same result, clean build. (Both edits reverted; `git status --short` confirmed a clean tree before and after.) This is the exact experiment the SUMMARY performed for the top-level `InviteBundle` case (and got a genuine `tsc` failure for) — repeated here for the held-entry case, with the opposite result.

The conformance suite's "or the conformance suite" fallback does not catch it either. Every probe in `invite-bundle-schema.test.ts` is generated by walking `Object.entries(...FIELD_RULES)` — by construction this can only test that a *declared* rule actually enforces its bound; it can never detect a field that exists on the real TypeScript type but has no table entry, because the test never looks at the real type, only at the table. The one test that comes closest, "every key a genuine `buildInviteBundle` output carries has a rule in the bundle table (builder coverage)" (lines 257-276), only walks `Object.keys(built)` — the **top-level** keys of a built bundle — never descending into `built.channels[0]`'s keys against `CHANNEL_KEY_FIELD_RULES`, nor into any `held` entry's keys against `HELD_KEY_FIELD_RULES`. There is no builder-coverage check for the two nested tables at all.

**Does this reopen CR-01's security property?** No — and this distinction matters for severity. `rebuildByRules` iterates `Object.keys(rules)` (the rule table's own keys), never `Object.keys(src)` (the input's keys), so a field with no rule is simply never copied to the output, regardless of whether TypeScript would have caught its absence. A *new* field on `held_roots`/`channels[].held` today ships as a **silent drop**, not a silent leak — CR-01's "no unbounded attacker string reaches the document" property survives this gap. What does not survive is D-17's own, explicitly-stated acceptance criterion: a missing bound is supposed to be *impossible to ship silently*, and for this one shape it demonstrably is possible — it just fails safe (data loss) instead of failing unsafe (unbounded leak). Given that `held_roots`/`channels[].held` are precisely the fields that caused 12.3-11 and 12.3-12's own misses, and given the whole premise of this round was "make this specific recurring failure structurally impossible," shipping the identical class of gap into the one mechanism built to prevent it is a BLOCKER against this round's own charter, not a cosmetic one — and a future legitimate protocol field silently vanishing for every joiner, with zero test or build signal, is a real (if lower-severity than CR-01) correctness defect in its own right.

**Fix:** give the real element types names in `types.ts` and derive the rule table from them, closing the gap the same way the other three tables are closed:
```ts
// types.ts
export interface HeldKeyEntry {
  epoch: number;
  key: string;
  refounder?: string;
}
export interface ChannelKey {
  id: string;
  key: string;
  epoch: number;
  name: string;
  held?: HeldKeyEntry[]; // was: Array<{ epoch: number; key: string }>
}
export interface JoinMaterial {
  // ...
  held_roots?: HeldKeyEntry[]; // was: Array<{ epoch: number; key: string; refounder?: string }>
}
```
```ts
// invite-bundle.ts
import type { HeldKeyEntry } from "../types.js";
export const HELD_KEY_FIELD_RULES: { [K in keyof Required<HeldKeyEntry>]: BundleFieldRule } = { /* unchanged */ };
```
Add a builder-coverage probe for the two nested tables, mirroring the existing top-level one — walk `built.channels` against `CHANNEL_KEY_FIELD_RULES` and any `held`/`held_roots` entries against `HELD_KEY_FIELD_RULES` — so this specific class of gap (a table exhaustive over the wrong type) has a *test-level* tripwire independent of the type-derivation fix.

### WR4-01 (WARNING): WR-08 (`handleRemoved` → `pruneDeadEntries()`) ships with no behavioral test — real but low residual risk

**File:** `packages/concord/src/client/client.ts:874-882`; absence noted in `client.test.ts` (no dedicated test; SUMMARY documents this as a deliberate, reasoned deferral).

**Issue:** I confirmed by direct reading (not grep alone) that `handleRemoved` genuinely calls `this.pruneDeadEntries()` at line 877, in the correct position (after tombstoning, before `saveMirror`/dirty-flag). The SUMMARY's own reasoning for not building a dedicated behavioral test is sound: reaching this path for real requires two live `ConcordCommunity` engines exchanging a genuine Refounding exclusion (the excluded party's own engine noticing its own removal via a real rekey-blob walk), and no existing test harness in this package provides that; building it is a separable, nontrivial effort. `pruneDeadEntries()` itself is pure and content-addressed (operates on `this.list`/`this.tombstones`, indifferent to which caller invoked it) and is exhaustively exercised via `leave()`'s own test battery, which mitigates — but does not eliminate — the residual risk.

**Real risk, stated precisely:** the untested surface is not "does pruning work" (well-covered) but "does this ONE call site, at this position, in this method, actually fire on the real code path." A future refactor of `handleRemoved` (e.g., reordering it relative to `removeCommunity`, or a merge conflict silently dropping the line) would have **zero test signal** — this is exactly the kind of one-line regression a grep-only verification (as the SUMMARY itself flags) cannot catch on its own in CI. Given this is one of the two mechanisms CR-02 depends on for a document to ever recover from a wedge, and the other two call sites (`leave()`, `reconcileCommunities()`) DO have direct tests, this asymmetry is worth closing rather than carrying forward a third time.

**Fix:** the minimum viable behavioral test does not require two live engines — it can drive `handleRemoved` directly (the method is private, but reachable via the `onRemoved` callback wired in `addCommunity`, which can be invoked synthetically in a test that constructs a community with an over-cap material and then calls the callback the same way a real Refounding-exclusion would). At minimum, assert that after an over-cap entry's `onRemoved` fires, the document is prunable exactly as `leave()`'s own tests already verify for the other two call sites. If this is judged out of scope for the next round too, it should be re-recorded (not silently re-deferred a second time) with the same explicit rationale.

### WR4-02 (WARNING): `checkKind`'s `held-list` handler makes `held_roots`'s "whole-bundle rejection" policy weaker than its own field-level table doc comment implies — worth a comment fix even though the behavior is correct

**File:** `packages/concord/src/helpers/invite-bundle.ts:393-399` (the `held_roots` rule's comment: *"a malformed OR over-cap array rejects the WHOLE bundle rather than dropping"*), `506-522` (the `held-list` `checkKind` case).

**Issue:** the comment at the `held_roots` rule assignment is accurate only for a **structurally** malformed array (non-array, over count, or an entry whose `epoch`/`key` fails) — it reads as though *any* malformed entry rejects the bundle, but a `held_roots[i]` entry with a valid `epoch`/`key` and only an oversized `refounder` does **not** reject the bundle; it is accepted with `refounder` silently stripped (per `HELD_KEY_FIELD_RULES.refounder`'s `drop`/`omit` disposition, correctly implemented — see the Adjudication below, where I conclude this is the *right* behavior). The comment's absolute phrasing ("ANY malformed entry" at line 510-511) oversells the guarantee relative to what the code actually does for this one sub-field, which is precisely the kind of doc/implementation gap WR-03 existed to close elsewhere in this same file.

**Fix:** soften the comment to name the asymmetry explicitly: *"held-list rejects the containing object when `epoch`/`key` cannot be rebuilt; a drop-disposition sub-field (`refounder`) is stripped instead, per that field's own rule."*

## Adjudications (requested)

### 1. `held_roots[i].refounder`: drop/omit (as shipped) vs. whole-bundle rejection (as one plan `<behavior>` bullet implied)

**Ruling: the shipped behavior (drop/omit) is correct; the plan's `<behavior>` prose bullet was the error.** Reasoning:

- `held_roots`'s *array-level* policy (reject the whole bundle on a structurally bad entry) exists because `buildInviteBundle` never emits `held_roots` at all — any `held_roots` at all is either a legitimate device's own historical material carried through some other path, or fabricated. That policy is about the entry's **identity-bearing** fields (`epoch`, `key` — what a chain element *is*), which is why both are `reject`/`reject` in `HELD_KEY_FIELD_RULES`.
- `refounder` is attribution-only (confirmed by tracing every consumer: `guestbook.ts:103`'s `d.author !== refounder` snapshot-honoring check, and `sync.ts:390-399`'s per-epoch attribution) — identical in kind and consequence to the top-level `refounder` field, which the same round already fixed as `drop`/`omit` for the same reason. Forcing whole-bundle rejection for a too-long *attribution* string, while every other attribution field in this same table (top-level `refounder`, `label`, `creator_npub`) drops instead, would be the inconsistent outcome, not the shipped one.
- I verified this is not a new gap: I diffed against the pre-D-17 (12.3-12) validator (`git show d98e8b30:...invite-bundle.ts`) and confirmed `held_roots` already validated successfully for a well-shaped `{epoch,key}` array (no `refounder` field existed to check at all in that round) — so "held_roots array present + individually well-formed entries validates" is a pre-existing, three-rounds-old design decision, not something this round weakened.
- The SUMMARY's own reasoning (compute the expected outcome from the rule's own disposition, never from independent prose, since the rule table — not the plan's prose — is what the conformance suite tests against) is the right normative anchor, and D-17 itself says the rule tables ARE the contract.

**Verdict: not a defect.** The plan's `<behavior>` bullet should be corrected for the historical record, but no code or test change is warranted.

### 2. WR-08's missing behavioral test

**Ruling: real risk, correctly classified as a residual gap, not a blocker.** See WR4-01 above for the full reasoning — the fix (`pruneDeadEntries()`) is present, correctly placed, and independently well-tested; only the "this exact call site actually fires" signal is missing, which is a maintainability/regression-safety gap rather than a currently-exploitable one.
