Close the two BLOCKERs and the folded warnings recorded in `12.3-REVIEW.md` (third

- **CR-01 (BLOCKER) — closed as a CLASS, per D-17.** `validateInviteBundle` bounds
  some fields and passes the rest through. Three rounds have now each bounded what
  their author happened to think of and missed the next field: 12.3-11 missed
  `held_roots`/`channels[].held` counts and `name` length; 12.3-12 missed `owner`,
  `owner_salt`, `refounder` and `relays[i]` length. This plan does NOT add four more
  named checks. It replaces the hand-maintained check sequence with **exhaustive
  declarative rule tables plus an allowlist rebuild**, so an unbounded string or
  array is unrepresentable: a field with no rule fails `tsc`, a rule with an
  unrecognised kind fails the conformance suite, and a field the walker does not
  copy cannot reach the output at all.
  The reviewed enumeration is *already* incomplete beyond the four fields the review
  named — `held_roots[i].refounder` and every unknown key on a `channels[]` or
  `held_roots[]` entry ride through by reference today. That is the direct evidence
  that enumeration is the wrong instrument, and it is why the rebuild (not another
  filter) is the fix.
- **CR-01's structural half — the aggregate bound.** Per-field caps multiply: 256
  channels x 64 held keys is legal under every cap and, at the NIP-44 plaintext
  ceiling, still yields ~64KB of material that the document serializes TWICE per
  entry (`seed` + `current`) into a 65535-byte cap. Per-field bounds alone cannot
  fix this. This plan adds a serialized-size bound at the validator AND at
  `recordJoin`, and a test that derives the whole ceiling chain from
  `LIST_MAX_BYTES` arithmetically, so a future cap change that breaks the chain
  fails the suite.
- **CR-02 (BLOCKER) — both halves.** (a) `leave()`'s prune sits behind
  `const community = this.communities.get(cid); if (!community) return;`
  (`client.ts:707-709`), so it cannot run in the engine-less wedge case it was
  written for — a fingerprint-suppressed unconstructable entry, or a `leave()`
  before `start()`/after `stop()`. 12.3-12's claimed must_have "a wedged list is
  recoverable through the public API" is therefore false. (b) `watchLists`'
  `mergeCommunities(this.list, communities)` (`client.ts:933`) is a never-deleting
  union, so a stale device re-inserts the pruned bytes and the document re-wedges.
  This plan makes the prune a property of the derived-dead state — idempotent,
  engine-independent, and applied on every path that kills a membership.
- **Folded warnings** (each judged in the scope table below): WR-01 sibling extras
  leak, WR-02 loopback carve-out, WR-03 stale doc comments, WR-04 duplicated byte
  measurement, WR-05 mislabelled merge diagnostic, WR-06/WR-07 test-validity
  defects, WR-08 `handleRemoved` divergence, IN-01/IN-02/IN-04/IN-05.

### The `pruneDeadEntries()` sketch, evaluated (not adopted as given)

The review proposes an idempotent prune driven off `isCommunityLive`, called from
`leave`, `handleRemoved` and `reconcileCommunities`. The core is right and this plan
adopts it, with three deliberate deviations that the executor must implement:

1. **The sketch drops `leave()`'s guard entirely.** Its `leave()` calls
   `this.communities.get(cid)?.leave()` with no early return at all, so
   `leave("anything")` would append a permanent tombstone for an unknown id — and
   tombstones are never pruned (CORD-02 §8). Keep a guard, but key it on the
   DOCUMENT rather than the engine map, which is precisely the reachability fix.
2. **The prune must NOT mark the list dirty or publish.** Its job is to keep the
   array that `saveCommunityList` serializes under the cap. If reconcile's prune also
   flagged dirty, a stale peer that re-publishes the entry on every churn would drive
   a publish per remote emission between two devices. Pruning silently and letting
   the next natural save carry the result avoids that loop entirely while still
   guaranteeing the document that eventually publishes is under cap.
3. **Call it from `reconcileCommunities`, not separately from `watchLists`.**
   `watchLists` already ends with `void this.reconcileCommunities()`, and an `async`
   method runs synchronously up to its first `await` — so a prune at the TOP of
   `reconcileCommunities` (before its `liveCommunities` read) executes inside the
   same synchronous turn as the merge, giving the review's "after the merge in
   `watchLists`" behaviour with ONE call site instead of two that could drift.

Liveness under CORD-02 §8 is preserved because the TOMBSTONE is never pruned: a
stale peer re-inserting the entry keeps its older `added_at`, which `isCommunityLive`
compares against the newer `removed_at`. A genuine re-join stamps a fresh, later
`added_at` in `recordJoin` — the designed resurrection path, unaffected.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| encrypted invite bundle -> `validateInviteBundle` | A bundle decrypted with a token the attacker also supplied. The `community_id` owner proof is SELF-CERTIFYING and authenticates nothing about length or cardinality: `communityId` feeds `owner` through `hexToBytes`, which imposes no maximum length, and the attacker computes the matching digest. Any plan step that assumes the proof constrains size is wrong. |
| validated bundle object graph -> `JoinMaterial` | Today the validator SPREADS its input and passes `channels[]`/`held_roots[]` entries through by reference, so unknown keys and un-inspected per-entry fields (`held_roots[i].refounder`) cross this boundary unbounded. The rebuild is what makes this boundary total. |
| `JoinMaterial` -> `recordJoin` entry -> serialized kind-13302 document | Where a stranger's chosen sizes become bytes in a document with a hard 65535-byte publish cap, duplicated across `seed` and `current`. Per-field caps multiply past this ceiling even when each one holds. |
| attacker invite fragment -> `decodeFragment` -> `pool.request` dial | Where an attacker's chosen relay string becomes an outbound socket. The plaintext-loopback carve-out currently makes localhost port probing reachable from a remote invite. |
| another device's / an older client's kind-13302 -> `watchLists` -> `mergeCommunities` | A never-deleting union re-entering this client on every cast emission, including entries this client version cannot construct and entries it has already left. |
| application-supplied `extraRelays` Observable -> engine constructors | A long-lived object the HOST application owns; a failed construction must never retain a subscriber on it. |
| `leave()` public API -> permanent tombstone | Tombstones are never pruned, so an unguarded `leave()` on an arbitrary id is an unbounded write into the user's own capped document. |
