The attachment parser and the tests added around media-key persistence were reviewed. The new diagnostic path still classifies cryptographically unusable AES-GCM nonces as valid encryption metadata, so callers can receive an `encryption` object that WebCrypto cannot decrypt.

## Critical Issues

### CR-01 [BLOCKER]: Invalid AES-GCM nonce lengths are reported as valid metadata

**File:** `packages/concord/src/helpers/imeta.ts:103`
**Issue:** `isHex(nonce)` accepts every non-empty even-length hexadecimal value, including a one-byte nonce such as `00`. `parseEncryption` consequently returns a populated `encryption` object and no `encryptionError`, even though WebCrypto rejects AES-GCM IVs shorter than 12 bytes with `OperationError`. This defeats the new malformed-metadata diagnostic contract and moves an input-validation failure into the consumer's decryption path. The module documentation also states that Concord uses a 16-byte nonce, but the parser does not enforce that encoding. The new tests only cover non-hex nonce text and therefore miss this boundary.
**Fix:** Validate the nonce's supported byte length before constructing `AttachmentEncryption` and add boundary tests for short, supported, and overlong values. If Concord's wire format requires its documented 16-byte nonce, use the exact-length form:

```ts
if (!isHex(nonce, 32)) {
  issues.push({
    field: "decryption-nonce",
    message: "Nonce must be 16-byte hexadecimal",
  });
}
```
