## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** Keep the containing message and attachment visible when encryption metadata is missing, malformed, or unsupported; attach a structured decryption error to the attachment instead of dropping either.
- **D-02:** A malformed attachment exposes one primary error with a safe message and field-level issues, while the complete raw `imeta` remains available separately for diagnostics.
- **D-03:** Detect invalid encryption fields during attachment parsing. Download and decryption failures discovered later may populate the same attachment error surface at the storage boundary.
- **D-04:** Preserve the current wire-level `encryption-algorithm`, `decryption-key`, and `decryption-nonce` field names, values, and tag layout exactly. Any normalized representation is internal only. — **Reversibility:** one-way — changing emitted tags would break interoperability with existing Concord, Vector, and 0xChat-compatible messages.
- **D-05:** Keep valid `MediaAttachment.encryption` behavior unchanged; add optional `encryptionError` and `rawImeta` fields rather than replacing it with a union or parse-result wrapper.
- **D-06:** `rawImeta` preserves the complete original tag, including unknown and duplicate entries. Normalized parsing may retain the current last-value behavior.
- **D-07:** Expose descriptive Concord error classes rooted at `MediaAttachmentError extends Error`, with specific subclasses such as unsupported-algorithm and invalid-field errors. Do not use opaque string codes or introduce a cross-package error base.

## Summary

The suspected epoch-key defect is not present in the current data model: a channel epoch key opens the sealed message rumor, but the blob's independent AES key, nonce, and algorithm are then read from that historical rumor's own `imeta` tag. `parseImeta` has no epoch-state input, and both epoch walkers retain and decode old message-plane wraps before routing rumors into their stores. [VERIFIED: `packages/concord/src/helpers/imeta.ts`, `packages/concord/src/client/sync.ts`, `packages/concord/src/client/channel-sync.ts`]

The verified defect is at the attachment parser boundary. Today any unsupported algorithm, missing encryption field, invalid key, or invalid nonce silently becomes `encryption: undefined`, which is indistinguishable from an intentionally unencrypted attachment. `parseImeta` is also currently unused by Concord production code, and Concord exposes upload but no download/decrypt storage API, so the phase should not invent a downloader merely to attach runtime errors. [VERIFIED: codebase grep; `packages/concord/src/helpers/imeta.ts`; `packages/concord/src/client/storage.ts`]

Plan this as two implementation slices: first make parsing lossless and diagnostic while preserving valid output and wire emission; then add genuine ciphertext round trips to the existing community and private-channel rotation harnesses. Those tests should fail if they substitute current epoch key material for the per-file key and should prove both old and new attachments decrypt after rotation. [VERIFIED: existing Vitest harnesses in `community.test.ts` and `private-channel.test.ts`; architecture inference]

**Primary recommendation:** Implement structured parse-time attachment errors in `helpers/imeta.ts`, leave `includeMediaEncryption` byte-for-byte unchanged, and prove the no-epoch-coupling invariant with real AES-GCM ciphertext in both rotation harnesses. [VERIFIED: codebase architecture]

## Architecture Patterns

### System Architecture Diagram

```text
Uploader returns per-file key/nonce
        |
        v
ChatMessageFactory -> base imeta -> includeMediaEncryption (wire fields unchanged)
        |
        v
bind channel+epoch -> seal rumor with epoch key -> relay wrap
        |
        +--> historical epoch walker chooses matching message-plane key
        |          |
        |          v
        |     decoded historical rumor
        |          |
        |          v
        +---- parseImeta -> MediaAttachment { encryption | encryptionError, rawImeta }
                                      |
                         consumer fetches ciphertext
                                      |
                         AES-GCM decrypts with per-file key/nonce
```

The two key domains are deliberately sequential, not interchangeable: epoch material opens the rumor; attachment material from that rumor opens the blob. [VERIFIED: code path analysis]

### Pattern 1: Presence-aware, lossless parsing

**What:** Parse the three recognized encryption keys with last-value semantics, but separately track whether any recognized field appeared. Zero recognized fields means an ordinary unencrypted attachment; partial or invalid fields mean `encryptionError`. Always preserve a shallow copy of the complete original `imeta` array in `rawImeta`. [VERIFIED: locked D-01, D-05, D-06; current parser behavior]

**When to use:** Every `imeta` tag that has a URL and therefore becomes a `MediaAttachment`. [VERIFIED: current `parseImeta` control flow]

```typescript
// Recommended internal shape; exact names remain planner discretion.
export interface MediaAttachmentFieldIssue {
  field: "encryption-algorithm" | "decryption-key" | "decryption-nonce";
  message: string;
}

export class MediaAttachmentError extends Error {
  constructor(message: string, readonly issues: MediaAttachmentFieldIssue[]) {
    super(message);
    this.name = new.target.name;
  }
}
```

### Pattern 2: Non-vacuous cross-epoch proof

**What:** Encrypt distinct known bytes for epoch N and N+1 with distinct random per-file keys/nonces; embed each tuple in its own rumor; rotate/refound through the real harness; retrieve both decoded rumors; parse each `imeta`; decrypt each ciphertext with only the parsed attachment fields. [VERIFIED: existing rotation harnesses; W3C AES-GCM contract]

**When to use:** Both community refounding and private-channel rekey regression cases. [VERIFIED: phase boundary]

The proof must assert old and new per-file keys differ from each other and from the epoch plane secrets. It should also include a negative control: decryption of the old ciphertext with the new attachment key rejects, proving the assertion is not merely reading plaintext or bypassing authentication. [VERIFIED: AES-GCM authentication behavior; test non-vacuity inference]

### Pattern 3: Additive public compatibility

**What:** Keep `encryption?: AttachmentEncryption`; add `encryptionError?: MediaAttachmentError` and `rawImeta?: string[]`. Valid encrypted attachments still expose the same normalized lowercase values, while unencrypted attachments remain error-free. [VERIFIED: locked D-05 and current code]

**When to use:** Public `MediaAttachment` evolution in this phase. [VERIFIED: phase context]

### Anti-Patterns to Avoid

- **Looking up blob keys from `community.material` or `ChannelKey`:** that couples attachment access to the current epoch and creates the defect the audit is designed to exclude. [VERIFIED: current per-file tag design]
- **Treating no encryption fields as malformed:** plain attachments are already valid; only partial presence or invalid/unsupported values should error. [VERIFIED: current optional encryption contract; locked D-05]
- **Reconstructing `rawImeta` from a normalized record:** this loses unknown entries, order, and duplicates. [VERIFIED: locked D-06]
- **Changing `includeMediaEncryption`:** D-04 requires exact wire compatibility; parser hardening does not require writer changes. [VERIFIED: locked D-04]
- **Adding a downloader API solely for this phase:** there is no current consumer/storage decryption seam to extend, and D-03 makes runtime attachment optional when such a boundary exists. [VERIFIED: codebase grep; locked D-03]
- **Logging raw metadata by default:** `rawImeta` contains the decryption key and must remain an explicit diagnostic surface, not automatic log output. [VERIFIED: current wire shape; security inference]

## Common Pitfalls

### Pitfall 1: A vacuous epoch test

**What goes wrong:** The test parses a hand-built tag after rotation but never retrieves a message through the historical epoch walker. [VERIFIED: testing topology analysis]

**Why it happens:** The tag parser itself has no epoch input, so a unit test always passes regardless of history routing. [VERIFIED: `parseImeta` signature]

**How to avoid:** Put the old attachment on a real pre-rotation wrapped rumor, complete the real rotation, then read the old rumor from the routed store and decrypt its external ciphertext. [VERIFIED: existing test seams]

**Warning signs:** No `start()`/sync walk, no rotated epoch assertion, or ciphertext/key variables created only after rotation. [VERIFIED: test-design inference]

### Pitfall 2: Conflating absent and malformed encryption

**What goes wrong:** Every normal unencrypted NIP-92 attachment gains an error, or partial encryption silently looks unencrypted. [VERIFIED: current optional attachment contract]

**Why it happens:** The current parser collapses all unsuccessful parse states to `undefined`. [VERIFIED: `parseEncryption`]

**How to avoid:** Track zero, partial, complete-valid, and complete-invalid states explicitly in the parser matrix. [VERIFIED: locked D-01/D-03]

**Warning signs:** A single truthiness check on `algorithm && key && nonce` with no recognized-field presence count. [VERIFIED: code-review heuristic]

### Pitfall 3: Mutating or normalizing the diagnostic input

**What goes wrong:** Duplicate fields or unknown entries disappear from `rawImeta`, defeating interoperability diagnosis. [VERIFIED: locked D-06]

**Why it happens:** A `Record<string,string>` intentionally collapses duplicates to the final value. [VERIFIED: current parser]

**How to avoid:** Retain `[...tag]` separately before building the normalized last-value record. [VERIFIED: JavaScript array behavior; locked D-06]

**Warning signs:** `rawImeta` is created with `Object.entries(entry)` or refers to a reconstructed tag. [VERIFIED: implementation inference]

### Pitfall 4: Leaking key material through errors

**What goes wrong:** A thrown error or log line includes the complete raw tag and therefore the blob decryption key. [VERIFIED: wire fields]

**Why it happens:** Diagnostics and user-safe error messages are represented by one string. [VERIFIED: error-surface analysis]

**How to avoid:** Error messages name invalid fields without values; keep `rawImeta` as a separate opt-in property on the attachment. [VERIFIED: locked D-02]

**Warning signs:** `JSON.stringify(tag)` in error constructors, snapshots, or logs. [VERIFIED: security inference]

### Pitfall 5: Over-scoping runtime failures

**What goes wrong:** The phase grows a fetch/decrypt subsystem with no existing public lifecycle, error propagation, or ownership contract. [VERIFIED: codebase inventory]

**Why it happens:** D-03 permits later storage errors on the same surface but does not require inventing a missing boundary. [VERIFIED: locked D-03]

**How to avoid:** Record the absent boundary explicitly; implement only parse-time errors and test-only decryption unless another live consumer is discovered during execution. [VERIFIED: codebase grep]

**Warning signs:** New production `fetch`, Blob, CDN, or object-URL APIs in the plan. [VERIFIED: scope inference]

## Open Questions

1. **Should `rawImeta` be present for every parsed attachment or only malformed ones?**
   - What we know: D-02 requires it for malformed diagnostics and D-06 defines exact preservation. [VERIFIED: locked context]
   - What's unclear: D-05 only says the field is optional. [VERIFIED: locked D-05]

2. **Which exact error subclasses should ship?**
   - What we know: D-07 requires a `MediaAttachmentError` root and descriptive specific subclasses. [VERIFIED: locked D-07]
   - What's unclear: Whether missing/invalid fields deserve separate classes. [VERIFIED: discretion statement]
   - Recommendation: Use `InvalidMediaAttachmentEncryptionError` for missing/invalid field issues and `UnsupportedMediaAttachmentAlgorithmError` for a present unsupported algorithm; both expose the same field-issue array. [VERIFIED: prescriptive design recommendation]

   - What we know: Only `ConcordUploader.upload()` exists in production; no fetch/decrypt consumer calls `parseImeta`. [VERIFIED: codebase grep]
   - What's unclear: Whether an unpublished downstream app owns a compatible boundary. [ASSUMED]
