# Phase 25.1: Concord Media Epoch-Key Decryption Audit - Context

**Gathered:** 2026-09-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Prove whether Concord attachments remain decryptable after community refounding and private-channel rekeying, then fix verified defects in attachment parsing or decryption. The audit starts from the existing design in which every encrypted attachment carries its own key, nonce, and algorithm inside the sealed message's `imeta` tag. CORD-07 voice transport and unrelated media capabilities remain out of scope.

</domain>

<decisions>
## Implementation Decisions

### Malformed Encryption Metadata
- **D-01:** Keep the containing message and attachment visible when encryption metadata is missing, malformed, or unsupported; attach a structured decryption error to the attachment instead of dropping either.
- **D-02:** A malformed attachment exposes one primary error with a safe message and field-level issues, while the complete raw `imeta` remains available separately for diagnostics.
- **D-03:** Detect invalid encryption fields during attachment parsing. Download and decryption failures discovered later may populate the same attachment error surface at the storage boundary.

### Compatibility Contract
- **D-04:** Preserve the current wire-level `encryption-algorithm`, `decryption-key`, and `decryption-nonce` field names, values, and tag layout exactly. Any normalized representation is internal only. — **Reversibility:** one-way — changing emitted tags would break interoperability with existing Concord, Vector, and 0xChat-compatible messages.
- **D-05:** Keep valid `MediaAttachment.encryption` behavior unchanged; add optional `encryptionError` and `rawImeta` fields rather than replacing it with a union or parse-result wrapper.
- **D-06:** `rawImeta` preserves the complete original tag, including unknown and duplicate entries. Normalized parsing may retain the current last-value behavior.
- **D-07:** Expose descriptive Concord error classes rooted at `MediaAttachmentError extends Error`, with specific subclasses such as unsupported-algorithm and invalid-field errors. Do not use opaque string codes or introduce a cross-package error base.

### the agent's Discretion
Exact subclass names, field-issue structure, safe error wording, and how runtime storage failures attach to the public surface are left to research and planning, provided they honor D-01 through D-07.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `parseImeta`: already centralizes recognized attachment parsing and is the natural source of parse-time structured errors and raw-tag retention.
- `includeMediaEncryption`: already preserves the interoperable wire vocabulary and decorates URL-matched base `imeta` tags.
- Community and private-channel epoch walkers: already retain historical message-plane keys, allowing the audit to exercise real cross-epoch decoding rather than constructing a parallel key lookup.

### Established Patterns
- Attachment blob keys are per-file values sealed inside the message rumor; they are not derived from the latest community epoch.
- Invalid metadata currently degrades to `encryption: undefined`, making malformed encryption indistinguishable from a genuinely unencrypted attachment.
- Concord package errors currently extend native `Error` or `AggregateError`; there is no repository-wide `ApplesauceError` hierarchy.

### Integration Points
- Extend `MediaAttachment` and `parseImeta` in `packages/concord/src/helpers/imeta.ts` without changing valid attachment output.
- Thread runtime download/decryption failures through the `ConcordUploader` or its consuming storage path only if the live code exposes such a boundary.
- Add regression coverage at the message factory/parser boundary and across both community and private-channel rotations.

</code_context>

<specifics>
## Specific Ideas

- Prefer descriptive error classes over codes that require consumers to look up their meaning.
- Preserve raw wire input so diagnostics never depend on a lossy normalized reconstruction.
