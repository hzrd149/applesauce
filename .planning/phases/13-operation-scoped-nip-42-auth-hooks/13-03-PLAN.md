<objective>
Thread `onAuthRequired`/`authTimeout`/`authRetries` through `SyncLoader` into both its negentropy sync
path and its paginated request path (RAUTH-08), keep the package's deliberate structural decoupling
(D-06), and make the loader's own stall guard and negentropy fallback auth-aware (D-16).

This plan resolves RESEARCH Open Question 2 and carries the loaders half of Open Question 3.

Purpose: `SyncLoader` is the consumer Phase 15's Concord engines reach the relay auth hook through; if
its 30s stall guard fires during an auth wait, or an auth-gated relay falls back to the paginated path
and burns a second request against the same wall, the hook is unusable in practice.
Output: mirrored auth types, three new fields on both option types, an auth-aware stall guard, a fallback
gated on error identity, and a test suite including the held-out slow-post-handler-wait case.

## Open Question 2 — SyncLoader stall-guard suspension: RESOLVED (stronger than the research's baseline)

`SyncLoader` owns the `onAuthRequired` value it threads into `methodOptions`, so it wraps the caller's
handler. The research's baseline (wrap the handler, suspend only while it executes) leaves the residual
window flagged as Assumption A2 — handler resolves quickly, `authSatisfied$` takes a while. This plan
closes that window instead of accepting it: the suspension opens when the wrapped handler is invoked and
stays open until the later of (a) the handler settling and (b) `authTimeout` milliseconds after it
settles, which is the maximum possible remaining duration of the relay-side auth phase because
`SyncLoader` is the one passing that same `authTimeout` down. When the caller passes `authTimeout: false`
the suspension is unbounded, which is exactly the semantics that caller opted into (D-14, D-16). Any
emission from the underlying stream also closes the suspension early, since events flowing means the auth
phase is over.

The held-out test VALIDATION.md reserves for that residual window — handler resolves fast,
`authSatisfied$` slow — is mandatory in Task 3 and must fail against a handler-execution-only suspension.

## Open Question 3 — loaders side of the error `.name` coupling

`SyncLoader` cannot import `AuthRequiredError`/`AuthHandlerError`/`AuthTimeoutError` (D-06), so it matches
`error?.name` against the exact strings `"AuthRequiredError"`, `"AuthHandlerError"` and
`"AuthTimeoutError"`. That set is declared once as a module-level constant with a comment recording that
it is coupled to the class definitions in `packages/relay/src/relay.ts` and must be updated together with
them. Plan 13-01 adds the mirrored comment at the definition site.

Give each relay stream its own auth-phase suspension signal and make `withTimeout` honour it.

Build the `onAuthRequired` that actually goes into `methodOptions` as a per-relay wrapper around the
caller's handler (when one is supplied). The wrapper opens the suspension immediately, delegates to the
caller's handler with the same context, and closes the suspension on the later of the handler settling and
`authTimeout` milliseconds after that — unbounded when `authTimeout` is false. An emission from the
underlying stream also closes it early. The wrapper must never swallow the caller's rejection: it
propagates so the relay layer maps it to a handler error. It must also never invoke the handler itself
beyond the single delegation, and must hold no state shared across relays.

Change `withTimeout` from a bare `rxTimeout({ first, each })` into a form whose clock does not advance
while that relay's suspension is open, preserving the existing first/each budgets and the existing disable
behavior when the timeout is falsy or zero. Because the suspension is per relay stream, the wrapper and
the timeout must be constructed inside `buildRelayStream` (or otherwise per url), not once for the whole
loader — a shared signal would let one relay's auth wait pause another relay's stall clock.

Gate the negentropy fallback: in the `catchError` that currently falls back to the paginated path for any
error, first check whether the error's `name` is in the auth error name set declared in Task 1. If it is,
re-throw so the error reaches the existing per-relay `catchError` and the relay is reported as errored,
rather than falling back — an auth-gated relay must not log a spurious sync-failure fallback and then burn
the request path against the same wall (D-16). Every other error keeps falling back exactly as today. Log
the suppressed-fallback case distinctly from the ordinary fallback so Phase 14 has something to attach to.

Add a comment at the suspension construction naming D-16 and the Assumption A2 residual window this design
closes, so a future reader does not reduce it back to handler-execution-only.
