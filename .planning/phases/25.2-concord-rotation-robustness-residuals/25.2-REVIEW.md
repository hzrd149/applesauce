## Summary

The rotation and Refounding implementation contains three ship-blocking correctness defects. Concurrent material transitions can overwrite each other's channel keys, concurrent community persistence callbacks can overwrite newer membership-list state, and private-channel post-adoption catch-up is not actually awaited. The scoped changesets satisfy the repository's one-change/one-sentence policy.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01: Concurrent channel transitions can discard an already committed key

**File:** `packages/concord/src/client/community.ts:938-945`

**Issue:** `prepareChannelKeyChange` snapshots `this.material` and derives a complete replacement `ConcordKeys` before awaiting persistence. Each private channel has its own rotation coordinator, so two channel rotations (or a channel rotation racing a root transition) can enter this method concurrently. Both derive from the same old material; after both persistence calls succeed, their returned commits assign their independent snapshots to `this.keys`. The later commit silently removes the earlier channel's newly adopted key even though that earlier key was already persisted and exposed. This is a key-state data-loss defect and can leave the child engine at an epoch the parent material no longer contains.

**Fix:** Serialize all root/channel material transitions through one community-level mutex/queue, holding the lane across derive, persistence, and synchronous commit. Derive from the latest committed `this.keys` only after acquiring that lane; do not let independent channel coordinators commit whole-state snapshots concurrently.

### CR-02: Concurrent community persistence callbacks lose newer list updates

**File:** `packages/concord/src/client/client.ts:874-888`

**Issue:** The callback computes `staged` from the current shared `this.list`, awaits `storage.setItem`, and then replaces `this.list` with that stale snapshot. Rotations in two communities can call this concurrently. If A and B both stage from L0, B can persist/commit L0+B and then A can persist/commit L0+A, erasing B's already successful material update from both memory and durable storage. The same race applies to other list mutations that occur while the storage write is pending.

**Fix:** Put all Community List mutations and mirror writes behind a single client-level serialized transaction. Inside that lane, recompute `staged` from the latest list, persist it, then commit that exact value before releasing the lane.

### CR-03: Private-channel catch-up returns before routing events and drops routing failures

**File:** `packages/concord/src/client/private-channel.ts:430-432`

**Issue:** `catchUpCurrent()` awaits only `syncAuthors`; it invokes async `onWrap()` without awaiting or collecting the returned promises. Consequently the coordinator's adoption finishes and latches the candidate while fetched events may still be pending. Any async event-store/rumor-store rejection becomes an unhandled promise rejection instead of reaching `failRotation`, and callers cannot rely on catch-up having completed when the method resolves.

**Fix:** Await routing before resolving, for example:

```ts
const events = await syncAuthors(this.syncContext(), [current]);
await Promise.all(events.map((event) => this.onWrap(event)));
```
