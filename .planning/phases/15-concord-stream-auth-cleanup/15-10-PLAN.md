<objective>
Close WR-03 and WR-04: the two places a NIP-42 auth problem currently disappears without a
trace.

**WR-03** (`auth.ts:98-117`): `onAuthRequired` `continue`s past every pubkey it holds no
signer for, with no log line and no `onAuthFailure` call. That is the exact mechanism that
turned CR-01 into a silent 30s `authTimeout` instead of a diagnosable failure. Because
`missingPubkeys` is always narrowed to the operation's OWN `waitForAuth`, a holder that
answers *none* of a non-empty `missingPubkeys` is definitionally a registration gap in this
scope — not a routine cross-scope skip.

**WR-04** (`invite-manager.ts:121`): `new StreamSigners()` with no options at all, unlike
`community.ts:359` and `private-channel.ts:173`. Revocation is the one operation whose silent
failure has a security consequence — a link the user believes is dead stays live — so it is
the worst place to drop the signal.

Purpose: WR-03 is the detection backstop for CR-01's whole defect class. Plan 15-09 closes
today's instance; this makes the next one loud on first occurrence rather than after a
verification pass.

Output: a total-answering-failure report on the holder, wired through the sink both engines
already fold into `error$` (D-13), and an invite manager that reports its own auth rejections.
</objective>

  <action>
In `StreamSigners.onAuthRequired`, track how many of the requested pubkeys this holder
actually answered. Keep the existing per-pubkey loop and its `continue` for an unheld pubkey
exactly as it is — the rejection semantics `auth.test.ts` pins are correct and must not
change. Add a counter (or an array of the answered pubkeys) incremented at the point a signer
is found and `relay.authenticate` is attempted.

After the loop, when BOTH of the following hold, report:

- `ctx.missingPubkeys` is an array (NOT `null`) and its length is greater than 0
- the answered count is 0

The report has two halves:

1. A distinct trace on the already-derived module-level `authLog` — do NOT call `.extend()`
   at the call site; the project's debug-logger convention requires the `Debugger` be derived
   once at module scope and reused, which `authLog` already is. The message should name how
   many pubkeys were requested and the relay URL, e.g. a format string with the requested
   count and `ctx.url`. Do not log the pubkeys themselves at full length; follow the file's
   existing 8-character truncation convention if any pubkey is included.
2. A call through `this.options.onAuthFailure` with a human-readable message stating that this
   scope holds no signer for any of the N pubkeys the relay asked about on that URL. Route it
   through the existing private `fail()`-style shaping if that reads cleanly, or add a sibling
   private method — either way the message must be distinguishable from the existing
   per-pubkey "relay rejected the AUTH" message, because they mean different things: one is a
   relay refusing a correct signature, the other is this scope being unable to sign at all.

Why the two guards matter, and why the condition is total-failure rather than any-failure:

- `missingPubkeys: null` means the operation asked for any authenticated user
  (`waitForAuth: true` — the NIP-59 Direct-Invite grant path, which the client-wide USER
  handler answers, not this one). The stream path authenticates nothing there by design; a
  report would be a false positive on every such publish.
- A partial answer is the legitimate cross-scope case. `community.test.ts`'s isolation oracle
  deliberately widens `missingPubkeys` to the union of two communities' authors; scope A
  answers its own and skips B's, which is correct behavior, not a gap. Reporting on any
  unanswered pubkey would make that oracle noisy and would train readers to ignore the signal.
- A total failure on a NON-EMPTY list is unambiguous: `missingPubkeys` is computed by the relay
  from *this operation's own* `waitForAuth`, which this scope named. Answering none of it means
  the scope declared a key it cannot sign for — CR-01's signature exactly.

Do not throw, do not reject, and do not change what is authenticated. The handler's contract
is unchanged; only its observability grows.

Update the class doc comment (or `onAuthRequired`'s doc comment) to state the new invariant:
a total answering failure on a non-empty request is reported, because under per-operation
narrowing that condition can only mean a registration gap in this scope.

Add three cases to `packages/concord/src/client/__tests__/auth.test.ts`, each constructing a
holder with a spy `onAuthFailure`:

- a holder registered with key A, invoked with `missingPubkeys: [B]` (B unheld) — asserts the
  spy received exactly one message and that `relay.authenticate` was never called
- a holder registered with key A, invoked with `missingPubkeys: [A, B]` — asserts
  `relay.authenticate` was called once for A and the spy received NO message
- a holder registered with key A, invoked with `missingPubkeys: null` — asserts
  `relay.authenticate` was never called and the spy received NO message
