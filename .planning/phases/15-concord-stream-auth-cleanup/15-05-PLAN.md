<objective>
Give every remaining `pool` operation in concord its own reactive auth options (D-01/D-15/D-16/D-17):
the nine publishes in `ConcordCommunity`, the community-list publish and two user-scoped reads in
`ConcordClient`, and the two publishes plus one read in `ConcordInviteManager`. Stream-authored
events are answered by the publishing scope's own holder; the two user-authored publishes and the
user's own list reads are answered by one client-wide user handler built once from the user's
signer (D-08).

Purpose: the user's framing for this phase is that "publishing should take the same reactive
authentication approach that we did with subscribing and syncing". The discovery that settles which
key each publish waits on is that a concord wrap is signed by the STREAM secret key — `buildWrap`
finalizes it with `streamSk` and the `p` tag decoy is the ephemeral part — so a gating relay checking
a write wants that stream key authenticated, not the user's (D-16).

Output: no publish or user-scoped read left that assumes something else already authenticated, and a
structural test proving every publish a community makes is answerable by that community's own holder.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| concord → relay (write path) | Signed events and the AUTH that gates them cross to relays, including transport-only extras. |
| user's signer (possibly a remote bunker or extension) → concord | The user handler may invoke a signer that prompts a human. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-10 | Spoofing | a publish declaring a `waitForAuth` it cannot satisfy, or satisfying it with the wrong key | high | mitigate | `streamPublishOptions(event)` derives the requirement from the event being published, so the declared author and the actual author cannot diverge. Task 3's loop proves the declared author is answerable by the holder that issued the publish. |
| T-15-03 | Spoofing / elevation | the user handler on user-authored publishes | high | mitigate | `createUserAuthHandler` authenticates only the thunk-resolved user pubkey; it is passed only at the four user-scoped sites and the one NIP-59 site, never at a stream-authored publish. Enforced by the acceptance-criteria greps that count its uses. |
| T-15-11 | Elevation of privilege (unintended signer use) | the two user-signed publishes and two user reads | medium | mitigate | D-17: neither user-signed publish is in a loop, so a prompting signer is asked at most once per save. Do not move `createUserAuthHandler` onto any looped site, and do not merge the stream and user handlers (D-09 keeps the prompting path separate from the never-prompting one). |
| T-15-12 | Information disclosure | the invite-link secret key registered into a holder | medium | mitigate | `addSecretKey` stores the key in memory only, never logs it, and the failure message carries an 8-character pubkey prefix. The existing rule that `link.token` is never logged stays untouched at every site. |
| T-15-04 | Tampering (concurrency) | concurrent AUTH for one key | low | accept | D-18 — unchanged. |
| T-15-05 | Denial of service (memory) | invite-link keys accumulating in a scope holder | low | accept | D-07 — the same accepted tradeoff; a long-lived community accumulates one key per invite link it minted or revoked. |

No package-manager installs occur in this plan, so no supply-chain row applies.
