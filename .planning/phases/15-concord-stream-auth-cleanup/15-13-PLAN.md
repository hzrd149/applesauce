<objective>
Close WR-07: `sync.ts:123` launders a genuine variance hole through
`ctx.onAuthRequired as unknown as SyncAuthHandler`.

`SyncContext` and `syncAuthors` are both public (`client/index.ts` -> `src/index.ts`).
`SyncContext.onAuthRequired` is typed `RelayAuthHandler`, whose context includes
`request: RelayAuthWireRequest`. The cast tells the compiler that any such handler is safe to
hand the loader — but `SyncAuthContext` (`packages/loaders/src/loaders/sync-loader.ts:62-75`)
has no `request` at all. Every in-package caller passes a `StreamSigners` handler that reads
only `missingPubkeys`, `relay.authenticate` and `url`, all of which `SyncAuthContext` carries,
and the default loader path routes through the pool so a real `RelayAuthContext` arrives in
practice. Nothing enforces either fact. A downstream consumer passing a handler that branches
on `ctx.request.verb` gets a `TypeError` the type system was asked to hide.

The review's remedy is to narrow `SyncContext.onAuthRequired` to the intersection the code
actually needs and wrap the holder once at the engine boundary. This plan takes the stronger
version of the same move: type the handler's PARAMETER to exactly the fields it reads, which
makes one function value assignable to both consumer handler types by contravariance — so
there is no cast at the loader boundary AND no adapter at the engine boundary. One handler,
one declared contract, zero assertions.

Purpose: the phase's whole thesis is that a scope answers only what it holds; a cast that
hides which fields the answer actually depends on is the type-level version of the same
ambiguity. This is also the last `as unknown as` on the auth path.

Output: a handler whose declared parameter is its real contract, and a `SyncContext` whose
type tells an external consumer the truth.
</objective>

  <action>
Declare, in `client/auth.ts`, a context type carrying exactly the three things
`StreamSigners.onAuthRequired` reads:

- `relay`: an object with the `authenticate` method the handler calls
- `url`: `string`
- `missingPubkeys`: `string[] | null`

Type it so that BOTH `RelayAuthContext` and `SyncAuthContext` are assignable TO it — i.e. it
must be a structural supertype of both. Take the `relay` member's shape from
`SyncAuthRelay` (the narrower of the two `relay` types) so a real `Relay` also satisfies it;
if the two packages' `authenticate` signatures differ in return type, declare the member with
the shape both satisfy rather than importing either package's concrete type.

Then declare the field so both consumers accept it:

`readonly onAuthRequired: RelayAuthHandler & SyncAuthHandler = async (ctx: <NarrowContext>) => { ... }`

This works by contravariance: a function whose parameter is a supertype of both context types
is assignable to both handler types. Verify the assignment compiles with no assertion — if TS
rejects the intersection form, fall back to declaring two separately-typed readonly fields
that both delegate to one private implementation, and record the reason in the SUMMARY. Do NOT
reintroduce an `as` assertion to force it.

The handler BODY does not change at all: same loop, same `continue` on an unheld pubkey, same
`relay.authenticate` call, same `onAuthFailure` reporting, same zero-answer report plan 15-10
added. Only the parameter's declared type and the field's declared type change.

Document on the new type that it is the handler's real contract — the fields it reads and
therefore the fields any caller must supply — and that this is why no cast is needed at either
boundary. Name explicitly that `request` is deliberately absent: `SyncAuthContext` does not
carry it, so a handler that branched on it would be unsound for the sync path.

Keep the new type inside `client/auth.ts`. It necessarily names `missingPubkeys`, and
`no-ambient-auth.test.ts`'s fourth check permits that identifier only in `client/auth.ts` —
declaring it anywhere else would turn the structural guard red, correctly.

`createUserAuthHandler` (`:129-154`) also reads `ctx.missingPubkeys` and `ctx.url` and calls
`ctx.relay.authenticate`, and is only ever used as a `RelayAuthHandler` (the pool paths). Leave
its type as `RelayAuthHandler` unless a caller in this repo actually needs it on the sync path
— widening it speculatively is scope creep. State in the SUMMARY which choice was made.
