### One release-facing item

**Phase 14 WR-06** is the only item that reaches users through something already written down.
`packages/relay/src/relay.ts:1286` manufactures the auth-exhausted `PublishResponse` as
`{ ok: false, from, message }` with no `error` field — a client-side give-up by definition. But the
D-11 comment three lines up at `:1238-1242`, and `.changeset/relay-publish-timeout-marks-itself.md`,
both state that the *absence* of `error` is the structural discriminator meaning "genuine relay
verdict." Independently re-confirmed live during this audit.

The changeset ships the sentence "callers can tell a client-side give-up from a relay rejection
without inspecting the message," which is not true while this path exists. **Either set the field or
correct the changeset and the two comments before the release goes out** — the release note and the
code have to agree. Backlog 999.16 already flags this as its highest-priority item and asks whether
it belongs in release prep rather than a backlog phase; this audit's answer is yes, release prep.

## Verdict

The milestone met its definition of done. NIP-42 auth is operation-scoped across all eight relay
operations, threaded through pool/group and both `SyncLoader` paths, instrumented end to end, and
Concord's client-wide registry and ambient relay drivers are gone with a structural guard watching

that 16 debt items had no home: Phase 13's and Phase 15's review residuals were each dispositioned in

That is not a tracking gap and not something archiving resolves — it is a decision about what
`applesauce-relay`'s next release says about itself, and it wants an answer before the release goes

future milestone can pick up on its own schedule.
