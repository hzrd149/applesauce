<objective>
Change `react`, `replyToThread`, and `deleteMessage` to take the full target `Rumor`
(D-01), and route each through the upstream machinery that already implements the CORD
rule — closing WIRE-03 (audit M15), WIRE-04 (M16), and WIRE-05 (L03).

All three defects have the same shape: concord hand-builds an identity object or a
pointer and hardcodes a kind, so the correct upstream path is never reachable. D-01
rejected both an in-engine plane-store lookup by id (which adds a target-not-yet-synced
failure mode whose graceful-degrade branch silently reinstates the bug) and a
`Rumor | { id; author }` union (which leaves the wrong path callable forever — the
enumerated-patch shape this project has repeatedly rejected).

`deleteMessage` is wrong even though its conclusion holds. See Task 1 for the correction.

override explicitly covers D-01's signature break, which the ROADMAP did not anticipate
when it named only the voice flag as this phase's breaking change.

Purpose: make the wrong path unrepresentable rather than adding a fallback branch —
the preference this project has confirmed repeatedly.

Output: three changed public signatures and one explicit `ensureKTag` application. The
fixture-anchored conformance assertions land in plan 11-05.

Change three signatures and three factory-argument constructions. Preserve the four-step
messaging shape verbatim in all three: `requireChannelKey(channelId)`, then
`channelEpoch(channelId)`, then the factory call, then `bindToChannel(channelId, epoch)`
applied to the awaited factory result, then `publishToPlane` with the plane target and an
empty options object.

Per D-01, use `Rumor` as the parameter type as-is. Add `Rumor` to the existing
type-import block that already pulls `ChannelKey`, `ChannelMetadata`, and friends from
`../types.js` (`types.ts` re-exports it from `applesauce-common/helpers`, and it is the
identical type `applesauce-core/helpers/event` exports — the same type
`channelStore(id).timeline(...)` already returns, so no call-site up-conversion is
needed). Do not invent a narrower structural type: `react` needs id/pubkey/kind while
`replyToThread` and `deleteMessage` also need `tags`, so there is no meaningful subset
smaller than `Rumor`.

1. `react(channelId, target, reaction)` — change the second parameter's type from the
   `{ id; author }` object literal to `Rumor`. Pass `target` itself as
   `ReactionFactory.create`'s first argument and delete the hand-built
   `{ id, pubkey, kind }` object entirely, including its hardcoded chat-message kind.
   `ReactionParent`'s union already accepts `Rumor`, and `setReactionParent`'s final step
   already calls `ensureKTag` with the parent's real kind — that is the whole of WIRE-03.

2. `replyToThread(channelId, parent, body)` — rename the second parameter to `parent` and
   change its type to `Rumor`. Pass `parent` itself as `CommentFactory.create`'s first
   argument and delete the hand-built event pointer entirely, including its hardcoded
   forum-thread kind. This makes `setParent` take its `"tags" in parent` branch, which
   calls `createCommentTagsForEvent` — the verbatim-root-inheritance implementation. Per
   D-03, the hardcoded kind is exactly why `setParent`'s comment-kind guard could never
   fire: the pointer mislabelled the parent, so depth-2 nesting silently re-rooted
   instead of failing loudly. Passing the real rumor makes the deeper-root walk via
   `getCommentRootPointer` reachable — that is the whole of WIRE-04.

3. `deleteMessage(channelId, target)` — change the second parameter from a bare id string
   to `Rumor`. This is the one place that needs a genuinely new line, and D-02's stated
   mechanism is WRONG here even though its conclusion holds:

   `setDeleteEvents` branches on `isEvent(event)`, which requires a string `sig`. A
   Concord `Rumor` never has one — that is the entire point of NIP-59 rumors — so passing
   the rumor object straight into `DeleteFactory.fromEvents` takes the bare-string
   else-branch and calls `ensureEventPointerTag` with the whole object as an id, which is
   both malformed AND still emits no `k` tag. WIRE-05 would survive D-01 unchanged.

   The correct fix, entirely inside concord: pass only `target.id` (a string) into
   `DeleteFactory.fromEvents` so the bare-string branch runs deliberately, await that
   factory to a plain template, then build a new template that keeps every other field
   and replaces `tags` with `ensureKTag(<the awaited template's tags>, target.kind)`, and
   hand THAT to `bindToChannel`. This is the identical "apply an `EventOperation`-shaped
   transformation to an awaited factory result" idiom the file already uses everywhere
   for `bindToChannel` itself, because `EventFactory` exposes only a protected `chain`.

   Import `ensureKTag` from `applesauce-core/helpers/factory` — it is already publicly
   exported there and is the exact function `setDeleteEvents`' own event branch calls. Do
   not write a concord-local equivalent.

   Do NOT cast the `Rumor` to a `NostrEvent` with a fabricated `sig` to force the
   `isEvent` branch. That lies about signature state on an object later code may treat as
   verified.

After these three edits the `kinds` namespace import is used at zero remaining sites in
`community.ts` — its only two uses are the hardcoded kinds being deleted. Remove `kinds`
from the `applesauce-core/helpers/event` import (keep `finalizeEvent`, `EventTemplate`,
and `NostrEvent`), or the build fails under this package's `noUnusedLocals`.

Do NOT edit anything under `packages/core` or `packages/common`. Per D-02 all three
factories already handle a full event or rumor correctly; a plan that edits upstream
factories for these three requirements has misread the problem.

Do NOT change `editMessage` — it stays on its bare-id signature and is not in
WIRE-01..05/11. Do NOT change `sendMessage`'s `replyTo` parameter — it routes to
`includeChatReply`, which emits only a NIP-C7 `q` tag and is correct as written; WIRE-04
concerns kind-1111 threaded replies, not NIP-C7 chat quote-replies. Do NOT widen any of
the three parameters to a union with the old shape.

Per D-09, do NOT create a changeset for these signature breaks.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied target rumor → published event tags | Values read off the target (`id`, `pubkey`, `kind`, `tags`) are copied into an event that is sealed, wrapped, and published. Nothing untrusted crosses a parsing boundary here — the target is a rumor the caller already holds from its own plane store — but a malformed copy becomes permanent on the wire. |

The three tag-shape requirements in this plan have no authentication, session,
access-control, or cryptographic surface. `requireChannelKey` is unchanged and still fires
before any factory is constructed, so D-01's signature change does not move the permission
boundary. No new incoming-data parsing is added.
