<objective>
Stop dropping kind 23313 voice presence at the receive funnel (D-04 / WIRE-02 / audit
M14), so a client can implement CORD-07 §4.

Today 23313 is decrypted, validated, and then silently discarded by an unconditional
`return` in the single receive funnel, with no alternative surface — an app cannot
implement presence at all, while the send direction works, so the SDK can emit presence it
can never receive. Kind 23311 (typing) is the contrast: it was never special-cased and
flows through this same path untouched.

Per D-04, delete the drop and route 23313 into the plane store like any other rumor.
Consumers read it via the already-public raw store, `channelStore(channelId)` with a
timeline filter on kind 23313 — exactly as the store's own doc comment already describes
for chat. Two symmetric sites, both go.

D-04 considered and REJECTED a dedicated time-windowed presence observable as
out-of-proportion for a requirement whose text is "reaches consumers instead of being
silently dropped". Do not build one — it is a Deferred Idea.

Per D-05, stale comments must be corrected alongside the deletion or they become false.

Purpose: this is the last plan in the phase; it lands after the messaging-method work so
the two edits to `client/community.ts` never race.

Output: two deleted lines, four corrected comments, and two receive-path tests.
</objective>
