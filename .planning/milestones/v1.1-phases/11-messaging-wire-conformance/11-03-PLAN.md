<objective>
Make the wrap's ephemeral decoy key caller-suppliable (D-07 / WIRE-11 / audit L10), so a
client can retain it and later NIP-09-delete its own giftwrap by `p` tag.

Today `buildWrap` generates the decoy keypair inline and discards the secret, permanently
foreclosing the CORD-01 §Deletions path: "They can also delete their own giftwraps by `p`
tag (on NIP-59-supporting relays) if the client saved the ephemeral key."

D-07 rejected the alternative of attaching the secret to the wrap via a non-enumerable
symbol — that follows the Phase 5.1 convention and needs no signature change, but it puts
a secret key on the object that gets published, the same shape 05.1's review flagged in
`lockAppData`. Explicit beats implicit for key material: the key is passed IN, never
handed back OUT.

Per D-08 this is retention only. Ship the plumbing plus a test proving the supplied key
round-trips to the emitted `p` tag. The NIP-09 giftwrap-delete flow itself is a consumer
concern and appears in no WIRE requirement — do not build it.

Purpose: this is the only requirement in the phase with a genuine key-material surface.
Everything else here is tag shapes.

Output: one new optional field threaded through exactly three signatures, plus a
round-trip and non-leakage test.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied secret key → published wrap | This is the phase's ONLY genuine key-material boundary. A secret `Uint8Array` enters `sendEvent`/`publishToPlane`/`wrapForTarget`/`wrapSeal`/`buildWrap` and must never cross back out into the event that gets published to relays, nor into a log sink. D-07 chose this shape precisely because the rejected alternative — a non-enumerable symbol on the wrap — attached the secret to the object that gets published. |
| local process → relay network | The wrap emitted by `buildWrap` is published to every relay in `transport()`. Anything serialized into it is public forever. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-07 | Information Disclosure | `buildWrap` (`operations/gift-wrap.ts`) | critical | mitigate | The supplied secret must never reach the published wrap. `buildWrap` binds the secret to a local, derives the decoy via `getPublicKey`, and places ONLY that public value in the `p` tag; the secret is not spread into the template, not serialized into `content`, and not returned. Verified by Task 2 case B asserting the wrap's JSON serialization does not contain the secret's hex, and by acceptance criteria confirming `GiftWrapOptions` was not widened (which would have exposed the field on `giftWrap`'s public surface). |
| T-11-08 | Information Disclosure | debug logging across the plumbing chain | high | mitigate | A log line taking the whole `opts` bag would write the secret to a debug sink. Mitigated by adding no log statement in this chain (D-11) and by a source gate: `grep -rnE '(console\.[a-z]+\|[Ll]og[A-Za-z]*)\([^)]*ephemeralSk' packages/concord/src` must return no lines. |
| T-11-09 | Information Disclosure | caller-supplied low-entropy or reused key | medium | accept | A caller could supply a weak or reused key, degrading the decoy `p` tag's unlinkability. D-08 is retention-only and states no validation requirement; enforcing entropy in the SDK is out of scope. Accepted and documented: the `WrapOptions` doc comment directs callers to obtain the value from `generateSecretKey()`, and the option accepts a `Uint8Array` rather than a hex string so a value cannot casually originate from user input. |

| T-11-SC | Tampering | package installs | — | n/a | This phase installs no npm/pip/cargo package (RESEARCH.md Standard Stack: "No new external packages are introduced by this phase... Package Legitimacy Audit is not applicable"). No legitimacy checkpoint is triggered. |
