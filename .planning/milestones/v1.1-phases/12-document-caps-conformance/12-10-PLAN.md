<objective>
Close **CR-01 (BLOCKER)** from `12-VERIFICATION.md` and `12-REVIEW.md`, together with **WR-01** and **WR-09**, at the channel-edition fold in `packages/concord/src/helpers/control.ts`.

Plan 12-08 implemented D-22's denylist-then-spread and, in doing so, deleted the two `typeof` guards the prior explicit-pick fold applied to `deleted` and `custom`. Both fields now ride through the rest-spread at any runtime type. An authorized `MANAGE_CHANNELS` holder — the exact actor the adjacent CHAN-04 comment models — publishes one edition carrying a `deleted` string, the terminal-deletion scan does not recognize it (that scan tests `=== true`), the channel is pushed into `CommunityState.channels`, and three loose-truthiness gates in `client/community.ts` then exclude it from stream-key registration, live reconciliation, and private sub-engine spawn — while `channels$` renders it. The channel is permanently visible-but-silently-dead on every client, with no deletion edition and no user-facing signal. This is a regression this phase introduced, on the exact mechanism (D-13/D-22's round-trip fold) the phase exists to harden, and it directly contradicts the phase goal's promise that shared state cannot silently destroy each other's data.

**Purpose — why a structural fix, reasoned explicitly rather than defaulted.**
This is the SECOND time this phase's denylist has been wrong about which fields it covers (CR-01 dropped two validations; WR-01 found `held` missing from the strip list while the comment beside it claimed exhaustiveness over `ChannelKey`). The defect CLASS is "a hand-maintained field list silently drifts from the real type," and Phase 12.3 burned four review rounds on exactly this class before plan 12.3-14 closed it structurally with `HELD_KEY_FIELD_RULES` keyed over the real type. Re-applying two `typeof` guards and appending one name to a string list would leave the class live for the third time.

The structural option was evaluated against the real declarations, not assumed viable, and one blocker was found and solved:

| Question | Answer |
|---|---|
| Is there a real type to key a rule table over? | Yes — `ChannelMetadata` (`types.ts:133-140`) and `ChannelKey` (`types.ts:168-178`). The parsed edition is `unknown`, but the fold's OUTPUT type is `ChannelMetadata` and the sensitive-name source is `ChannelKey`; both are named, exported interfaces. |
| Does a naive mapped type over `ChannelMetadata` enforce anything? | **No — and this is the trap.** `ChannelMetadata` carries `[k: string]: unknown` (added by 12-08), so `keyof Required<ChannelMetadata>` is `string \| number` and a mapped type degenerates to an unenforcing index signature. Solved with a key-remapping alias (`DeclaredKeysOf<T>`) that drops index-signature keys, leaving exactly the five declared names. |
| Does it close Phase 12.3's known CR5-01 caveat (a rule's `kind` not bound to the field's type)? | **Yes.** Each rule carries a `ChannelFieldGuard<V>` type predicate whose asserted type is the slot's declared field type, so a boolean guard in a `Record` slot is a compile error. This design does NOT inherit 12.3's limitation. |
| Does it also cover the `ChannelKey` half WR-01 names? | Yes, and more strongly than the review's own suggested fix. The review proposed `satisfies readonly (keyof ChannelKey)[]`, which only checks that listed names ARE keys — it exits 0 when a new `ChannelKey` field is forgotten, which is the defect. A total map over `keyof Required<ChannelKey>` fails instead, and the escape-hatch classification is type-restricted to names `ChannelMetadata` declares, so a new sensitive field cannot even be classified as safe. |

All four mechanisms were compile-verified against TypeScript 5.9.3 under this package's `strict` + `noUnusedLocals` settings before this plan was written; Task 3 requires the executor to reproduce every one of them in-repo.

Output: two total, type-derived rule tables and a rule-driven `foldChannelEdition` in `helpers/control.ts`; six regression tests (two of them generated from the tables, so a future field gets coverage automatically); and five executed probe transcripts.

    **1a — the two type-derivation helpers.**

    Add an exported generic type `DeclaredKeysOf<T>` implemented as a key-remapping mapped type over `keyof T` whose `as` clause maps a key to `never` when `string extends K`, when `number extends K`, or when `symbol extends K`, and to `K` otherwise.     **1b — the type-bound rule vocabulary.**

    Add an exported generic type `ChannelFieldGuard<V>` equal to a function type taking `unknown` and returning the type predicate `value is V`.

    Add an exported generic type `ChannelFieldRule<V>` as a discriminated union on a `disposition` member with exactly three variants: `"derived"` carrying no other member (the field's value comes from the fold's own coordinate, never from edition JSON); `"required"` carrying a `guard: ChannelFieldGuard<V>` (a guard miss rejects the whole edition, matching today's `continue` behavior); and `"optional"` carrying a `guard: ChannelFieldGuard<V>` (a guard miss OMITS the field and keeps the channel).     **1d — the rule-driven builder.**

    Add a module-private function `foldChannelEdition` taking a `Record<string, unknown>` and the entity id `eid`, returning `ChannelMetadata` or `undefined` (`undefined` meaning "this candidate is rejected; try the next," preserving today's `continue` semantics exactly).

    It builds the result as ONE construction from two ordered entry lists, never by per-key bracket assignment and never by a rest-spread:
    - the pass-through list: every own entry of the parsed object whose key is neither in `CHANNEL_KEY_STRIPPED_FIELDS` nor a key of `CHANNEL_METADATA_FOLD_RULES`;
    - the declared list, built by iterating `CHANNEL_METADATA_FOLD_RULES`: a `derived` rule contributes the entity id; a `required` rule contributes the parsed value when its guard accepts, and otherwise causes the function to return `undefined` immediately; an `optional` rule contributes the parsed value when its guard accepts and contributes NOTHING otherwise.

    Concatenate pass-through entries FIRST and declared entries LAST and materialise with `Object.fromEntries`. Two properties depend on those exact choices, and the comment must say so: later entries win, so a hostile edition's own `channel_id` still cannot shadow the coordinate-derived one (the invariant plan 12-08's Test C pins, preserved here by construction rather than by spread ordering); and `Object.fromEntries` uses data-property creation, so an edition carrying the prototype-setter key does not alter the result's prototype — a per-key bracket assignment loop WOULD, which is a hazard the previous rest-spread did not have and this refactor must not introduce.

    Iterating the rules will require one widening step to read a heterogeneous table generically — confine it to a single local annotated `ChannelFieldRule<unknown>` at the top of the loop body and comment that this is the only erasure, deliberately contained, with the enforcement living in the table's declared type.
