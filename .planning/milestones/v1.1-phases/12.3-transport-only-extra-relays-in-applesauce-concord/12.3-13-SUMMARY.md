# Phase 12.3 Plan 13: D-17 Rule-Table Rewrite of validateInviteBundle, the Aggregate Entry-Size Ceiling, and the Derived-Dead-State Prune Summary

**`validateInviteBundle` rewritten as four exhaustive mapped-type rule tables plus a generic rebuild-never-spread walker (D-17), closing CR-01 as a class rather than a fifth named check; a per-entry serialized-size ceiling at `recordJoin` closes CR-01's structural half; `pruneDeadEntries()` makes the Community List's dead-membership byte-prune reachable with no running engine and idempotent against re-merge (CR-02); `ConcordPrivateChannel`/`InviteWatcher` gained the same self-cleaning constructor `ConcordCommunity` already had (WR-01), and the extras-merge diagnostic no longer misreports a normalization collapse as a parse failure (WR-05).**

## Accomplishments

- **D-17 closed structurally.** `validateInviteBundle` no longer contains a hand-maintained per-field check sequence. Four exported, exhaustive mapped-type rule tables (`INVITE_BUNDLE_FIELD_RULES`, `CHANNEL_KEY_FIELD_RULES`, `HELD_KEY_FIELD_RULES`, `BLOB_POINTER_FIELD_RULES`) declare every field's bound; a generic `rebuildByRules` walker REBUILDS the validated object from them (never spreads the input), so a field the tables do not name — known or unknown — cannot reach `JoinMaterial`. A field added to any of the four source interfaces with no rule fails `pnpm --filter applesauce-concord build`; demonstrated by hand (see below).
- **CR-01 closed as a class, not four fields.** `owner`, `owner_salt`, `refounder`, every `relays[i]`, and every unknown key at any depth (including inside `channels[]`/`held_roots[]` entries) are bounded or stripped by the SAME mechanism the review's own enumeration missed twice already. New caps `INVITE_BUNDLE_MAX_RELAY_URL_LENGTH` (512) and `INVITE_BUNDLE_MAX_TOTAL_BYTES` (8192).
- **CR-01's aggregate half closed.** `COMMUNITY_LIST_MAX_ENTRY_BYTES = Math.floor(LIST_MAX_BYTES / 2)` (community-list.ts) is enforced at `recordJoin` before the engine is constructed or `this.list` is touched, so no single join — however legal under every per-field cap — can push a Community List entry over half the document cap.
- **CR-02 closed on both halves.** `pruneDeadEntries()` drops the bytes of every derived-dead membership; it is called from `leave()` (guard now keyed on the DOCUMENT, not the engine map — reachable for a fingerprint-suppressed unconstructable entry or a leave after `stop()`), from `handleRemoved` (WR-08), and at the top of `reconcileCommunities` (ahead of the never-deleting `mergeCommunities` merge, closing the durability half).
- **WR-06/WR-07 restored by genuine coverage, not deletion.** The engine-first `recordJoin` ordering now has a test (a throwing store factory driven with a FULLY VALID bundle) that fails when the ordering is reversed — demonstrated by hand. The stale-remote-copy test now stamps its fixture strictly newer than the leave-time publication (so the merge genuinely happens) and asserts three independent facts instead of a trivially-satisfied disjunction.
- **WR-01/WR-05 folded in.** `ConcordPrivateChannel` and `InviteWatcher` constructors are now self-cleaning like `ConcordCommunity`; the merge diagnostic checks each relay entry's own parseability instead of comparing set sizes, closing a false positive that fired in this project's own pre-existing test suite.
- **Deferred (documented, not missed):** IN-03, the `icon` URL-scheme policy, organic entry growth past the per-entry ceiling, and WR-09 all remain deferred per the plan's own scope table, unchanged from prior rounds. WR-08's code-level fix is complete but has no dedicated behavioral test (see Deviations).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `ExtraRelays.merge`'s WR-05 fix, as literally suggested by the review, is mathematically dead code**

- **Found during:** Task 5, while implementing the review's suggested `mergeRelaySets(base, this.current)` vs `mergeRelaySets([...base, ...this.current])` size comparison
- **Issue:** `mergeRelaySets` flattens ALL of its source arguments into one `Set` regardless of how those sources are grouped (two separate array arguments vs one pre-concatenated array). The two calls the review's own "Fix" code block suggests therefore always produce identical-length results — the diagnostic could never fire, silently defeating the entire point of WR-05 (still no diagnostic for a genuinely unparseable entry).
- **Fix:** implemented a semantically correct check instead — count how many of the raw input strings fail to parse INDIVIDUALLY (`mergeRelaySets(entry).length === 0` per entry), which correctly distinguishes a genuine parse failure from a normalization-driven collapse, independent of deduplication.
- **Files modified:** `packages/concord/src/helpers/relays.ts`
- **Verification:** both new relays.test.ts cases pass (no log for a trailing-slash collapse; a log for a genuinely unparseable entry), and both were observed failing/behaving differently against a literal implementation of the review's original snippet during development.
- **Committed in:** `c015c1db` (Task 5 commit)

### Descoped / Deferred (documented, not missed)

**2. [WR-08] No dedicated behavioral test for `handleRemoved`'s prune**

- **Found during:** Task 4, while writing the required "handleRemoved prune test"
