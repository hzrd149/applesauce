<objective>
Close WR-03 and WR-04 in `packages/loaders/src/loaders/sync-loader.ts`.

**WR-03** is the same defect *class* this whole gap-closure round exists to sweep — an advertised
guarantee that is silently absent on one path. D-16 promises that the loader's stall guard does not run
during an auth wait. Today that suspension is only ever opened from inside `relayOnAuthRequired`
(`sync-loader.ts:417-443`), and that wrapper is `undefined` whenever the caller supplied no
`onAuthRequired`. D-14 is explicit that the auth phase exists with or without a handler — a relay that
answers `auth-required:` makes the relay layer wait up to `authTimeout` (default 30s) for out-of-band
auth either way. So a handler-less caller gets a 30s relay-side wait racing a 30s loader-side stall
clock, and whichever fires first decides the user-visible outcome. The guarantee is conditional on an
option that has nothing to do with it.

**The structural choice, stated up front:** do not fix this with an `if (handler)` special case. The
wrapper becomes unconditional and its declared type becomes non-optional, so "no wrapper installed" is
not representable and the phase accounting cannot be bypassed by an absent option. When the caller
supplied nothing the wrapper delegates to nothing and returns `undefined` — which `authRetry` folds into
the exact same `of(undefined)` it already produces for a missing handler (auth-retry.ts:247-248), so the
relay-side semantics are unchanged. This is the same discipline as making a defect class
unrepresentable rather than patching the next instance of it.

**WR-04** is the resource-lifetime half of the same code. `scheduleClose()` arms
`setTimeout(close, authTimeout ?? 30_000)` and drops the handle on the floor. Nothing clears it: not
`close()`, not `forceCloseAuthPhases()` (which calls `close()` and drops the callback from the set but
leaves the armed timer), not the relay stream ending. Every auth phase therefore leaves a timer pending
for up to 30s after the loader is torn down, keeping a Node process alive and running phase bookkeeping
against a finished run. **Two further leak paths exist beyond the one the review names, and this plan
closes all three** — see Task 2.

Purpose: WR-03 makes D-16's headline property false for the default configuration (no handler), and
WR-04 makes every auth-gated load leave a live timer behind. Both live in a file this round already
owns; deferring them would mean a second gap-closure round on the same file.
Output: an auth-phase wrapper that cannot be bypassed by an absent option, a phase timer that cannot
outlive its phase, and four tests each of which fails against today's code.
</objective>

  <action>
Retain the phase's timer handle in the phase closure and clear it when the phase closes. `close()` is
already the single idempotent exit point — it flips `closed`, removes itself from `pendingAuthCloses`,
decrements the counter and signals the change — so clearing the handle belongs there, guarded on the
handle actually being set, and the handle is dropped afterwards so it cannot be cleared twice.

That alone does **not** make the timer safe. Audit the paths that end a phase and close all three of
these, do not assume `close()` is the only one:

1. **A phase that settles after it was already closed.** `forceCloseAuthPhases()` runs on every stream
   emission, so a slow handler is routinely still pending when its phase is force-closed. When that
   handler finally settles, `scheduleClose()` runs against an already-closed phase and arms a fresh timer
   that nothing will ever clear — `close()` early-returns on the `closed` flag when it eventually fires,
   and the callback is no longer in `pendingAuthCloses`. Make `scheduleClose()` a no-op for a phase that
   is already closed. This path leaks a timer even when the loader run is completely healthy.
2. **A handler that throws synchronously.** The delegation is not currently guarded, so a synchronous
   throw propagates out of the wrapper before `scheduleClose()` is reached: no timer is armed, but the
   phase is never closed either, so the suspension stays open and the stall guard stays disarmed for that
   relay until some later emission force-closes it. Plan 13-08 made this shape a real, mapped case rather
   than a theoretical one. Close the phase on the synchronous-throw path and re-raise the original error
   untouched — the relay layer must still see it and map it to its handler error class. Do not swallow
   it, and do not convert it into a value.
3. **The relay stream ending with a phase still open.** Add a finalize step to `buildRelayStream`'s
   terminal pipeline that force-closes every remaining phase, importing `finalize` from rxjs. Place it in
   that pipeline, not inside `withTimeout`: `withTimeout` returns the source unwrapped whenever the stall
   guard is disabled, so a hook placed there silently disappears for those callers. Confirm by reading
   rxjs's finalize semantics — and by the Task 3 teardown test — that it runs on unsubscribe as well as on
   complete and error, rather than assuming it.

Update the block's comments to state the new invariant: a phase owns at most one timer, that timer never
outlives the phase, and the phase never outlives the relay stream. Keep the existing D-16 rationale
comments intact.

Do not change `withTimeout`'s own timer bookkeeping — its `clearArmed`/teardown handling is already
correct and is out of scope here.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| relay WebSocket -> `SyncLoader`'s per-relay stall guard | An auth-gated relay controls how long the auth phase lasts, and therefore how long the loader's own clock must stay suspended |
| `SyncLoader` auth phase -> the host event loop | Timers armed per auth phase, per relay, per load are host resources the calling application never sees and cannot cancel |
