<objective>
Close WR-02 and WR-06 on `RelayGroup`.

`RelayGroup.request()` (group.ts:243-272) is the group's most-used read API and the one path in the
phase that never received D-15's operation-clock suspension: it calls `relay.req(filters, {...opts,
reconnect})` without threading an `AuthPhaseGate`, and keeps a bare `timeout({ first: opts?.timeout ??
30_000 })` where every other operation clock in the phase was converted to `suspendableTimeout`.
`RelayPool.request()` delegates straight to it (pool.ts:185-190), so the gap covers the pool too.

This gap was latent until now: the group stream also carries `req()`'s `OPEN`, so the bare `timeout`'s
first-emission gate was satisfied immediately and the clock never fired either way. Plan 13-08 fixed
that class at the source. **That makes WR-02 live rather than latent** — a group request whose auth
prompt takes longer than the request timeout will now be killed by a clock that has no reason to be
running during an auth phase. This plan must land in the same phase as 13-08, not after it.

WR-06 is a small consistency fix in the same file: `RelayGroup.sync`'s D-19 per-relay catch writes
directly to the console instead of going through the package's `debug` logger, which a consumer cannot
switch off. `Relay`, `negentropy.ts`, `management.ts` and `liveness.ts` all derive a logger once at
class or module scope; `RelayGroup` has none.

Purpose: RAUTH-07's pool-and-group leg is only structurally true today — the options are forwarded, but
the D-15 property the phase advertises is absent from the group's main read path.
Output: a group request whose clock suspends across the auth phase, proven by a test that fails without
the gate, and a group logger consumers can silence.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| relay WebSocket -> `RelayGroup.request()` fan-out | Each relay in the group independently controls whether it demands auth and whether it ever answers; one hostile or slow relay affects the shared group clock |
| library diagnostics -> host console | Library code writing directly to the console cannot be silenced by the consuming application |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-11-01 | Denial of Service | `RelayGroup.request()` operation clock, group.ts:262 | high | mitigate | Task 1's gate threading plus Task 3's suspension test. Plan 13-08 makes this clock fireable for the first time; without the gate an auth prompt slower than the request timeout kills every group read, turning a latent gap into a live self-inflicted outage on the most-used read API in the package |
| T-13-11-02 | Denial of Service | `RelayGroup.request()` against an unresponsive relay | medium | mitigate | Task 3's clock-fires test. An unfireable group clock lets a relay that accepts a REQ and stalls pin the whole fan-out subscription with no error surfaced |
| T-13-11-03 | Information Disclosure | direct console write in `RelayGroup.sync`'s D-19 catch, group.ts:334 | low | mitigate | Task 2 routes it through the package logger. A relay url and an error object — potentially including an auth failure reason — are written to the host console unconditionally, with no way for the embedding application to suppress them |
