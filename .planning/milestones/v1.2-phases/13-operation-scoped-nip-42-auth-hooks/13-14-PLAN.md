<objective>
Close CR-02 from `13-REVIEW.md`: `RelayGroup.request()`'s first-emission gate accepts the group's own
per-relay `ERROR` bookkeeping as relay progress, so the operation clock is cancelled by a relay that
produced nothing.

**Structural choice (stated explicitly per planning directive 1):** this is not a new defect class —
it is WR-01 (`req()`'s synthetic `OPEN` counted as progress) reappearing one layer up, at the exact
site plan 13-11 was written to fix. Plan 13-08 made `isProgress`/`firstWhen` **required** parameters
precisely so a call site could not answer this question by accident. That guardrail did not fail; it
was bypassed. `group.ts:275` reads:

```ts
firstWhen: (message: GroupReqMessage) => isReqProgress(message as RelayReqMessage),
```

`GroupReqMessage = RelayReqMessage | GroupReqErrorMessage` (types.ts:254). The `as RelayReqMessage`
cast erases the `GroupReqErrorMessage` arm, so `isReqProgress` — which only knows how to say
`type !== "OPEN"` — sees `type: "ERROR"` and answers `true`. The fix is therefore **not** to add an
`ERROR` special case inside `isReqProgress`; that would push a group-layer concept into a relay-layer
predicate and leave the cast in place for the next arm. The fix is to make the group's predicate
**total over its own union with no cast**, so the compiler is back in the loop: adding any future
group-only message arm becomes a type error at this site instead of silently defaulting to "progress".

**Explicitly rejected alternative:** widening `isReqProgress`'s parameter to `GroupReqMessage`. That
makes every relay-layer call site accept a value it can never receive, and re-opens the same
"predicate is more permissive than its call site" gap one level down.

Task 2 then audits the rest of `group.ts` and `pool.ts` for the same cast-then-delegate shape, so the
mechanism is swept rather than this one instance being patched.
</objective>

Add a module-scope predicate in `group.ts`, beside or above the `RelayGroup` class:

```ts
/**
 * The group-level progress predicate (CR-02). `GroupReqErrorMessage` is a value the group manufactures
 * for itself in `internalSubscription`'s `catchError` when a relay's stream fails — it means that relay
 * produced *nothing*, so it is bookkeeping rather than progress, exactly as `req()`'s synthetic `OPEN`
 * is at the relay layer (WR-01). Narrowing instead of casting keeps the compiler responsible for this
 * question: a new arm added to `GroupReqMessage` fails to typecheck here rather than silently counting
 * as progress.
 */
export function isGroupReqProgress(message: GroupReqMessage): boolean {
  if (message.type === "ERROR") return false;
  return isReqProgress(message);
}
```

The narrowing is load-bearing and must not be replaced by a cast: after the `ERROR` early return,
TypeScript narrows `message` to `RelayReqMessage`, so `isReqProgress(message)` typechecks *because*
the union has been exhausted. If a third arm is ever added to `GroupReqMessage`, that call becomes a
compile error — which is the whole point of this plan.

Then rewrite the `suspendableTimeout` call in `request()` to pass it directly:

```ts
suspendableTimeout(opts?.timeout ?? 30_000, gate, { firstWhen: isGroupReqProgress }),
```

Delete the `as RelayReqMessage` cast and the inline arrow entirely. Rewrite the comment at 268-273: it
currently asserts that the OPEN-exclusion check "applies identically" to `GroupReqErrorMessage`, which
is the incorrect conclusion that produced this defect. It must now state that ERROR is not progress and
why.

Import `isGroupReqProgress`'s dependencies as needed; `isReqProgress` and `GroupReqMessage` are already
imported in this file (lines 42 and 52 import the types; confirm `isReqProgress` is imported too and add
it if not).

Do NOT modify `isReqProgress` in `relay.ts`. Do NOT widen its parameter type.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| relay WebSocket -> `RelayGroup.request()`'s operation clock | A relay controls whether it errors, stalls, or answers, and therefore whether the group's single shared clock is cancelled |
| `GroupReqMessage` union -> the progress predicate | The group's own manufactured values travel the same stream as relay-originated ones; only the predicate distinguishes them |

## STRIDE Threat Register

_ASVS L1; `high` and above are blocking._

|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-14-01 | Denial of Service | ERROR accepted as first emission, group.ts:274-276 | high | mitigate | Task 1's total predicate, proven by Task 3 Test 1. Today a single failing relay cancels the group's only clock, so a group whose remaining relays fall silent never errors and never completes — the caller's `timeout` option is silently void. Any relay can trigger it by failing its connection, which is the ordinary case this code path exists to handle |
| T-13-14-02 | Tampering | cast at a predicate boundary defeating a required-parameter guardrail | high | mitigate | Removing the `as RelayReqMessage` cast restores compile-time enforcement, and Task 1's verify step proves it by adding a probe arm and observing the build fail.
