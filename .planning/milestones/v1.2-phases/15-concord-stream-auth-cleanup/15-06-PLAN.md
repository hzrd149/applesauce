<objective>
Migrate the last consumer of the client-wide auth class. `InviteWatcher` holds no stream keys at
all — it constructs the class purely to get `autoAuthenticate`'s `pool.status$` subscription — so it
takes D-08's user handler and nothing else (D-09). Its inbox reads gain `waitForAuth` plus that
handler; `autoAuthenticate` disappears from both the watcher and `ConcordClient`, and with it the
last two of CAUTH-03's relay-status-driven auth readers.

**A ruling this plan makes explicit.** CONTEXT.md's `<canonical_refs>` lists `authenticateUser()`,
`userNeedsAuth()`, and the flag readers at both call sites as source under change, while its
`<code_context>` note says the `autoAuthenticate: false` test "documents the manual
`authenticateUser()` path that must keep working". Those two cannot both be satisfied literally:
the flag readers ARE the bodies of those two methods, and both methods are proactive by
definition — they authenticate before any relay has refused anything, which D-01 rules out
("authenticates only when a relay actually refuses it"). So both `authenticateUser()` and the
`needsAuth$` indicator derived from `userNeedsAuth()` are removed, and what "keeps working" is the
capability, not the method: a gating inbox relay still gets the user's AUTH, now on demand from the
read it refused. Concord is unreleased, so this public-surface removal costs nothing downstream.

Purpose: after this plan the class scheduled for deletion has zero consumers, which is what makes
plan 15-07's deletion a pure removal rather than a migration.

Output: an invite watcher with no ambient auth, a client with no `autoAuthenticate` gate, and the
example's manual-authenticate banner gone.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| inbox relay → invite watcher | Discovered NIP-17/NIP-65 inbox relays are third-party endpoints the user did not necessarily choose; they can refuse reads and thereby trigger the user's signer. |
| user's signer (bunker/extension) → watcher | The handler may prompt a human. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-06 | Spoofing (cross-scope) | the removed flag readers | high | mitigate | Removal is the mitigation: `userNeedsAuth()` counted a relay as needing auth from `authRequiredForRead`/`authRequiredForPublish`, which any other scope's refusal on a shared relay can flip. No new reader of either flag is introduced anywhere. |
| T-15-13 | Elevation of privilege (signer abuse) | a hostile inbox relay refusing reads to force AUTH prompts | medium | mitigate | The handler runs only in response to a refusal of the watcher's OWN read, and the `authRetries` default of 1 bounds it to one auth cycle per operation per connection (D-05). The previous ambient loop could re-fire on every status emission from every relay in the merged set — narrowing to refusal-driven is a reduction, not a new exposure. |
| T-15-03 | Spoofing / elevation | the watcher's user handler | high | mitigate | Its own `createUserAuthHandler` instance authenticates only the thunk-resolved user pubkey; proven by the "unrelated pubkey records no AUTH" assertion. |
| T-15-14 | Repudiation / availability | removing the manual authenticate affordance | low | accept | An app that wants a pre-emptive "authenticate now" button no longer has one. Accepted: D-10's deferred idea records the demand-driven per-relay record as the shape to build if an app asks, and D-01 rules out proactive auth in this phase. |
| T-15-04 | Tampering (concurrency) | concurrent AUTH for the user key | low | accept | D-18 — unchanged. The watcher's two operations can each trigger one AUTH for the same identity. |
