<blockers>

**CR-01 (confirmed) — every private-channel publish declares an unanswerable `waitForAuth`.**

`deriveConcordKeys` (`helpers/keys.ts:181-189`) populates `keys.channels` for public *and* private channels — only keyless private channels are skipped. `planeKeyFor` (`helpers/keys.ts:219-223`) therefore resolves a private channel's message-plane stream key for `wrap.pubkey`. `streamPublishOptions` emits `{ waitForAuth: [wrap.pubkey], onAuthRequired: this.signers.onAuthRequired }`, but the community's holder is registered (`community.ts:753-759`) with core planes + `publicChannelKeys()`, which filters `!c.private` (`community.ts:719-724`). That key lives only on the sub-engine's separate holder.

Effect on an auth-gating relay: the handler authenticates nothing, the publish waits out the 30s `authTimeout`, `publishToPlane`'s `.catch` swallows it, and the optimistic echo at `community.ts:1612` renders the message as sent. This is a **regression** — pre-phase the publish carried no options (`waitForAuth: true`) and the deleted registry did hold private channel keys via `channel-sync.ts`'s `registerStreamKeys`.

`streamPublishOptions` already logs `"publishing wrap=%s with no registered signer for author=%s"` on exactly this state; it fires on every private-channel send and was read as benign.

**The human-verify approval does not cover this.** The six approved steps exercised `rumor-stores`, `crypto-history`, `direct-invites`, and `admin-management`; none performed a private-channel send against an auth-gating relay.
</blockers>
