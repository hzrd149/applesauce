# Plan 14-08: Harden the auth log against hostile relay input, and align the new lines with what they assert

## Objective

Close the code-review BLOCKER (CR-01) and the four warnings that make a freshly-shipped log line
assert something the code does not establish (WR-01, WR-02, WR-03, WR-04).

Phase 14's whole purpose is that an operator can trust the `:auth` trace. CR-01 defeats that: every
relay-controlled string (NIP-42 challenge, `CLOSED` reason, `OK` message) is interpolated into the
string handed to `debug` as its **format** argument, so a hostile relay can erase its own log line's
content or forge an extra line that is byte-identical to a genuine `Relay accepted AUTH for <pubkey>`
line. Verified against the real `debug@4.4.3` in this workspace.

Read `.planning/phases/14-auth-lifecycle-debug-logging/14-REVIEW.md` for the full findings —
**CR-01** (line 67), **WR-01** (124), **WR-02** (151), **WR-03** (174), **WR-04** (198). The review
records exact file:line locations, the empirical repro, and a suggested fix shape for each.

## Tasks

### Task 1 — Neutralize relay-supplied text at the shared formatter (CR-01)

Harden the shared formatter in `helpers/auth-log.ts` so that relay-supplied free text can neither be
interpreted as a `debug` format specifier nor introduce a new physical line. Apply it where all seven
sinks already flow, not at the sinks.

Cover both vectors directly in `helpers/__tests__/auth-log.test.ts`. Prove non-vacuity: revert the
hardening with the Edit tool, watch the new tests fail, restore it, watch them pass. Record the exact
failure output in the SUMMARY.

Commit atomically.

### Task 2 — Prove it end-to-end against real debug output (CR-01)

Extend `__tests__/auth-lifecycle-logging.test.ts` so both vectors are proven against real captured
`debug` output from a live `Relay` — the existing T-14-01 oracle only exercises `"x".repeat(...)`,
which is exactly why this shipped. Use the existing `debug-capture.ts` harness; do not build a second
capture mechanism.

The forging vector's oracle must assert that a hostile `CLOSED` reason cannot produce a second
captured line, since a bare substring assertion would pass even while forged.

Commit atomically.

### Task 3 — Make the four new lines match what they assert (WR-01, WR-02, WR-03, WR-04)

- **WR-04** — make auth log-line construction incapable of throwing into the operation's critical
  path. A diagnostic defect must degrade the line, not fail the operation. This also protects the
  CR-04 handler-error mapping.
- **WR-01** — `event()`'s refusal line is currently gated one-shot per connection; make it per-refusal
  so it matches `req`/`count`/`negentropy`.
- **WR-02** — `resetState()`'s line counts AUTH *attempts* (including `response: null` and `ok: false`)
  while calling them "authenticated pubkeys". Make the count and the wording agree.
- **WR-03** — the AUTH-sent line is emitted before anything reaches the socket. Move it so it reflects
  a write that actually happened.

WR-01 and WR-03 change when lines are emitted, so update 14-06's oracles in step. Update assertions to
the new correct emission point — never weaken or delete an oracle to make it pass.

Commit atomically.
