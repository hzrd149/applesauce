<objective>
Give `Relay` a dedicated `:auth` sub-namespace, retire the last two internal readers of the bucketed
auth-required flags, and log the full NIP-42 connection track — challenge received, signing, AUTH sent,
result — plus the auth-state invalidation that a reconnect causes.

Purpose: ALOG-01 asks that an operator can tell from debug output where an auth attempt sits and why it
ended the way it did. Today a `Relay` emits one bucketed line per connection and nothing else, so a hung
signer and an unresponsive relay are both silence (D-09), and the expected re-auth-per-reconnect cycle is
invisible behind a bare disconnect line (D-12).

Output: an `authLog` field on `Relay`, four connection-track lines, a guarded `resetState` invalidation
line, the four relay-side refusal lines rerouted with their request summaries, and the two one-shot
bucketed log subscriptions deleted.
</objective>

Use the full 64-character pubkey wherever a pubkey appears — it is D-08's join key between this track and every operation's track, and unlike relay-supplied text it is caller-derived, fixed-width, and not attacker-controlled, so it is not truncated. Relay-supplied strings (the challenge, the OK message) always go through `truncateForLog`.

1. **Challenge received** — in the `ListenForChallenge` pipeline's `tap`, replace the existing base-logger call with an `authLog` line stating that the relay sent a NIP-42 auth challenge, carrying the challenge through `truncateForLog`. Keep the `this.challenge$.next(challenge)` update in the same `tap`, unchanged.

2. **Signing** — in `authenticate()`, immediately after the challenge guard and immediately before `signer.signEvent(...)`, log that an AUTH event is being signed for the current challenge and that the call is now waiting on the signer. Include the truncated challenge so the line ties to the challenge line above it. This method is the only place signing happens, which is why the line lives here rather than in `auth()` (D-10).

3. **AUTH sent** — in `auth()`, before the `lastValueFrom(...)` call that subscribes and writes the AUTH frame, log that the AUTH event is being sent for the event's pubkey, naming the pubkey in full. Phrase it in the present progressive so it stays accurate whether or not `waitForReady` defers the actual socket write. Placing it in `auth()` rather than inside `event()`'s send side effect means a consumer who signs their own AUTH event and calls `auth()` directly still gets this line (D-10), and it avoids gating a line on a verb check inside the generic publish path.

4. **Result** — inside `auth()`'s existing `tap`, after the keyed `authentications$` update and the deprecated mirror write, log the outcome: accepted or rejected, the full pubkey, and the relay's own OK message passed through `truncateForLog` as the "why" (D-09). Do not reformat or reinterpret the relay's message; carry it as given, only bounded.

Log only the pubkey and the message — never the signed AUTH event object, which would put a full event with its signature into prose output for no diagnostic gain (RESEARCH's V6 row).

Do not add any relay-scoped bookkeeping that would let this track name which operations its AUTH satisfied. The relationship is many-to-many by protocol, and each operation names its own satisfying pubkeys from its own side (D-08); relay-scoped in-flight-phase state is exactly what RAUTH-05 forbids.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| relay WebSocket → `Relay` | the NIP-42 challenge, the `CLOSED`/`NEG-ERR` reason and the `OK` message are attacker-controlled free text, and all three are interpolated into connection-track and refusal lines by this plan |
| signer → `Relay` | `authenticate()` hands a caller-supplied signer an event template and receives a signed event back; the signed event is state, not log content |
