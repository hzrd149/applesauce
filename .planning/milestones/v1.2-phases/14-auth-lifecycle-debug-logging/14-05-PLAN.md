<objective>
Make every state a blocked operation sits in, and every way it can end, readable from the shared auth
operator's own output — each line stamped with the wire key of the request that triggered it and the
phase number within that operation's retry budget.

Purpose: ALOG-02 requires that retry, timeout and rejection outcomes are attributable to the specific
operation that caused them. The operator is where every one of those outcomes is decided, and today it
emits exactly one line for the whole phase. Without per-state lines, a blocked attempt is silent about
what it is blocked on (D-14), and two concurrent operations' outcomes are indistinguishable in a shared
stream.

Output: a per-phase line set in `operators/auth-retry.ts` keyed by wire request plus `phase n/N`, and
operator-level tests asserting the line set for each outcome path.
</objective>

Hoist `const context = config.buildContext(signal.reason);` to be the first statement of `runPhase`, above both early returns, and delete the later duplicate assignment. `buildContext` is a pure assembly over current relay state with no side effects, so moving it is safe, and it is what gives the two early-return paths a request label to log. Directly beneath it derive two per-phase locals: `const requestLabel = describeWireRequest(context.request);` and a `phase` label built from the counter, described below.

Define the phase label as `phase ${consecutive}/${authRetries}` — the counter as it stands *after* the increment for the phase being logged, over the configured budget. Read the arithmetic off the existing code rather than assuming: the operator gives up when `consecutive >= authRetries` *before* incrementing, so a call configured with the default budget of 1 runs exactly one phase and that phase is `phase 1/1`. Introduce a small local helper inside `authRetry`'s `defer` closure — for example `const phaseLine = (text: string) => config.log?.(\`${requestLabel} — ${text}\`)` scoped so it can see `requestLabel` — so every line in this plan shares one prefix and one call shape. Keep the optional-call form (`config.log?.(...)`) at the single point where the injected logger is actually invoked; do not make `log` required.

Now write the blocked-state lines D-14 enumerates:

1. **Phase begins** — replace the existing single log call inside the `phase$` defer, immediately after `config.gate.begin()`. Keep every existing control-flow construct byte-for-byte as it is — the `gate.begin()`/`finalize(gate.end())` pairing, the synchronous-throw `try`/`catch`, the `catchError` mapping, the `filter`/`take(1)` wait, the `ignoreElements()` wrapper. This plan adds observation only.

Add one line per terminal outcome, each on the `phaseLine` prefix so it carries the request label:

1. **Opted out (RAUTH-06)** — in `runPhase`'s `waitForAuth === false` early return, before constructing the terminal error: state that the relay requires auth for this request but the operation opted out of waiting, so no handler was invoked and the request fails. This path never runs a phase, so it carries no phase counter.

2. **Retries exhausted** — in `runPhase`'s `consecutive >= authRetries` early return, before constructing the terminal error: state that the operation's auth budget is spent, naming how many phases ran. Also carries no phase counter of its own; the count it names is the budget that was exhausted.

3. **Wait satisfied** — attach a `tap` immediately after the `filter`/`take(1)` pair that resolves the `authSatisfied$` wait, and log that the wait was satisfied together with the pubkeys `config.satisfiedPubkeys()` reports at that moment. This is D-08's join key printed from the operation's side; when the list comes back empty, say so explicitly rather than emitting an empty fragment (a boolean requirement satisfied by a race can legitimately report nothing). Call `satisfiedPubkeys` at this point and not earlier — it must reflect the state that resolved the wait.

4. **Handler threw or rejected** — two lines, one in the synchronous `catch` block and one in the `catchError` that maps a rejected promise, each naming which of the two happened and carrying the cause's message through `truncateForLog`. Keeping them distinct is what tells an operator whether the handler failed before it ever returned or after; both still map to the same terminal error, which is unchanged.

5. **Per-phase timeout** — inside the `timeout({ with: ... })` factory, before the terminal error is constructed, state that this phase exceeded its budget, naming the configured millisecond value and that the budget covered both handler execution and the subsequent wait. The `authTimeout === false` branch stays unlogged — an unbounded wait has no timeout event to report.

Explicitly do **not** log at the source pipe's `tap` that sets `consecutive = 0`. D-07 decided the counter reset gets no line of its own precisely because the per-line phase counter restarting at 1 already makes it observable. Add a short comment at that `tap` recording the decision so a future reader does not "fix" the apparent omission.

Do not change the operator's control flow, its retry arithmetic, its gate handling, or its error mapping. Every added line is a statement inside an existing branch or a `tap` that passes its value through unchanged.
